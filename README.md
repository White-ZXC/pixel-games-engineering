# pixel-games-engineering

四款像素 / 沙盒游戏的**工程与设计**分析，写成可顺序阅读的中文长文。

这不是攻略，也不做玩法评测。它想回答的是同一个问题在四个项目里的四种答案：

> 一款游戏在**技术上是怎么被造出来的**、**为什么这样设计**、**一个开发者能从中怎么学**。

选这四款，是因为它们共享一个前提——都没有换成通用商业引擎，各自用自研或半自研的方案走到了今天，但代价和收益完全不同。把它们放在一起看，"自研引擎"这件事才会从一个口号变成一个可以被逐项比较的工程决策。

---

## 四款游戏，一句话

| 游戏 | 一句话定位 | 技术基底 |
|---|---|---|
| **Minecraft Java 版** | 一个 voxel 专用自研引擎 + 一层数据驱动的内容层 | Java + LWJGL 3，1.17 起全 shader |
| **星露谷物语** | 用 C# 手写的、数据驱动的 2D 生活模拟引擎 | C# + XNA 4.0 → MonoGame |
| **泰拉瑞亚** | 跑在 XNA/FNA 之上的自研 2D 格子动作 RPG | C# + XNA 4.0 → FNA |
| **饥荒（DST）** | 小型 C++ 运行时 + 大规模 Lua 玩法层 | C++ 引擎 + Lua 玩法 |

## 阅读顺序建议

**第一次读：按顺序。**

```
minecraft → stardew-valley → terraria → dont-starve → comparison
```

理由是前面四篇各自把一款游戏讲透，`comparison.md` 才有对照的素材；反过来先读对照，会觉得结论来得没有依据。

**第二次读：按维度横切。** 直接进 [横向对照](docs/comparison.md) 的某一节，例如只看"资源与构建管线"或"世界结构 → 联机难度"，再回各篇找细节。

**只想读一篇：** 如果时间只够一篇，读 [横向对照](docs/comparison.md)。它自带四款游戏的最小必要背景。

## 三条学习路线

四篇文档里的"动手项目"被重新编排成了三条路线，按**你想要的终点**选，而不是按起点难度选。

| 路线 | 训练什么 | 适合谁 |
|---|---|---|
| **A. 2D 格子向** | 数据布局、渲染与光照、状态机、网络同步 | 想做 2D 沙盒 / 动作游戏 |
| **B. 内容驱动向** | 内容管线、数据建模、存档迁移 | 想做"内容量大、系统多"的游戏 |
| **C. 脚本引擎向** | 运行时注入、状态机、服务端 / 客户端边界 | 想做"玩法迭代快、有 mod 生态"的游戏 |

三条路线的完整项目清单、验收标准和顺序建议在 [横向对照 · 第 9 节](docs/comparison.md#9-如果要自己动手三条可执行路线)。

每条路线的项目都设计成**可独立验收、可回退**，前一步不是后一步的硬前置（除非文中注明）。

## 关于证据等级

四篇文档都用同一套标记区分信息可信度，读的时候请留意：

| 标记 | 含义 |
|---|---|
| **【官方】** | 官方公告、更新日志、文档、明确访谈 |
| **【社区·可查】** | 社区文档、反编译阅读、游戏文件可验证 |
| **【推断】** | 基于工程常识与可见产物的推理 |
| **【存疑·待考】** | 无法确证、版本有出入 |

横向对照里另有一档 **【对照推断】**，专指"只有把四家放在一起比较才得出的新结论"，不与源文档的事实断言混在一起。每篇结尾都有各自的存疑清单。
