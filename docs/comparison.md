## 1. 技术谱系总览

### 1.1 一张总表

| 维度 | Minecraft Java | 星露谷物语 | 泰拉瑞亚 | 饥荒 / DST |
|---|---|---|---|---|
| 语言 | Java | C# | C# | C++（引擎）+ Lua（玩法） |
| 框架/引擎 | 自研引擎 + LWJGL 3 | XNA 4.0 → MonoGame | XNA 4.0 → FNA | 自研 C++ 引擎 |
| 起步年份 | 2009 | 2012 | 2011 | 2013 前后（DST 2014 EA） |
| 跨平台手段 | JVM + LWJGL（JNI） | MonoGame + 外部移植团队 | FNA 重实现 XNA API | C++ 平台层，Lua 逻辑不动 |
| 渲染路径 | 1.17 起 OpenGL 3.2 core，全 shader | DirectX 11 / OpenGL 等（随 MonoGame） | FNA3D → OpenGL 等 | 自研 |
| 是否换过引擎 | 否（只换图形/运行时层） | 否（只换运行时：XNA→MonoGame） | 否（只换平台层：XNA→FNA） | 否 |
| 关键改动性质 | 渲染管线重写 + 数据格式重构 | 运行时迁移 + 位数升级 | API 重实现 + 音频/着色器改造 | 平台层移植 |

### 1.2 同样"不换通用引擎"，四套理由完全不同

这是本文第一个要拆开的地方。四家都坚持自研或半自研，但动机不是同一条。

**Minecraft：需求正交 + 深度耦合 + 生态锁定**

- voxel 的区块网格化、按距离流式加载、逐方块光照、海量小批次合并，在通用引擎里要写大量自定义代码，收益还不如自己写。【社区】
- 更硬的一条是"耦合"：方块更新、光照更新、区块加载次序**直接参与游戏规则**（红石顺序、光照影响刷怪）。抽成通用引擎等于把"规则"和"实现"分离，成本极高。【社区/推断】
- 再加一条生态锁定：mod API 的稳定性建立在"类名、方法签名、调用点"上，换引擎等于让生态归零。【社区】

**星露谷：不是主动不换，是"能跑就不动"**

- 2012 年立项时 XNA 是独立开发者做 2D 游戏最完整的 C# 技术栈。【访谈】
- 2013 年微软停更 XNA 后，Windows 版仍能跑；对单人项目，迁移收益（64 位、跨平台统一）长期小于风险（存档、渲染、音频、mod 兼容）。【推断】
- 真正推动统一的是**mod 的内存上限**和**双运行时带来的双倍维护**：32 位进程约 2GB 地址空间，大型整合很容易触顶。【官方方向 + 推断】
- 结果：2021-11-30 的 1.5.5 把 Windows 主分支从 XNA 迁到 MonoGame 3.8 + 64 位 .NET 5，1.6 再升 .NET 6。【官方】

**泰拉瑞亚：不是"引擎能力不足"，是"引擎只需要让开"**

- 核心玩法就是"二维格子表 + 每格光照 + 海量内容 ID"。这套东西在自研循环里是几个数组 + 几层循环；塞进通用引擎的 Tilemap 反而要跟抽象打架。【推断，理由充分】
- 内容管线是资产不是代码：几千物品、几百 NPC、上千配方围绕"整数 ID + 数据表"组织，迁移等于重建整个加载/序列化/ID 体系。【推断】
- 确定性优先：世界生成、Boss AI、联机同步都依赖"同样输入同样结果"，自研循环里每个 tick 完全可控。【推断】
- 团队规模：核心个位数到十几人，重写引擎等于停更两三年，买断制游戏不可接受。【官方方向】

**饥荒：2012–2013 年的通用引擎做不了它的美术**

- 当时的通用引擎不擅长"2D 剪纸骨骼动画 + 瓦片世界"：角色由几十个可旋转部件组成、每帧按曲线插值、还要支持换装。【推断】
- Klei 此前做过《Shank》《闪克 2》《忍者印记》，已有 2D 动画与手感积累。【推断】
- 小团队需要"少一层抽象"：通用引擎的抽象层对高度特殊的项目反而是调试成本。【推断】
- 可移植性：C++ 引擎 + Lua 逻辑，移植只重写平台层，玩法逻辑不动。【官方+推断】

> **【对照推断】四条理由其实分属两类。**
> - **被动型**（星露谷、泰拉瑞亚）：不是"自研更好"，而是"改成通用引擎的边际收益为负"——沉没成本在内容管线、数据结构和存档格式里，不在渲染代码里。
> - **主动型**（Minecraft、饥荒）：自研能直接换来通用引擎给不了的东西——MC 是区块/光照/网络的极致特化，饥荒是剪纸骨骼动画管线的贴合。
> - 一个可直接操作的判据：**如果迁移的代价主要在"资产与数据结构"，那是被动型；如果代价主要在"能力缺口"，那是主动型。**

### 1.3 真正的共同模式：换平台层，不换内容架构

四家都换过东西，但换的位置惊人一致：

| 游戏 | 换掉的那一层 | 没动的那一层 |
|---|---|---|
| Minecraft | LWJGL 2→3（1.13）、固定管线→OpenGL 3.2 core（1.17） | 方块/区块/存档/世界生成的数据模型 |
| 星露谷 | XNA→MonoGame、32 位→64 位、.NET 5→6 | 地图/数据表/事件脚本/存档对象图 |
| 泰拉瑞亚 | XNA→FNA、XNA 音频→FAudio、HLSL→MojoShader→GLSL | 格子世界、ID 体系、.wld/.plr 格式 |
| 饥荒 | 平台后端（主机/移动端移植） | Lua 玩法层、Prefab/Component 结构 |

> **【对照推断】这是四份文档里最值得合并的一条工程规律：**
> **"不换引擎"的真实含义不是"拒绝现代化"，而是把可变性收敛到平台层，把内容与规则层冻结。** 平台层可以每几年重写一次（风险可控、玩家不可见、CI 可验证），内容层一旦重写就会连带摧毁 mod 生态、存档兼容和玩家记忆。
> 反过来说，**任何"重写内容层"的更新都是高危更新**——这解释了三件事：MC 1.13 的 Flattening 为什么让生态痛了很久；星露谷 1.6 的 ID 重构为什么要配迁移与降级警告；泰拉瑞亚为什么要死守"只追加 ID"。

### 1.4 代价清单对照

| 游戏 | 自研/半自研的主要代价 |
|---|---|
| Minecraft | GC 停顿、JIT 预热、缺值类型、JNI 边界成本【社区】 |
| 星露谷 | 32 位内存墙、双运行时维护、迁移期 mod 大面积失效【官方+推断】 |
| 泰拉瑞亚 | 多一条运行时路径、图形/音频 bug 变成"平台相关"、双后端长期验证【推断】 |
| 饥荒 | 工具全自建、招聘难、平台认证/崩溃上报/性能分析自担、Mod API 安全边界自己设计【推断】 |

> **【对照推断】** 这四份代价清单指向同一个反直觉结论：**自研引擎省下的不是钱，是"抽象层摩擦"；付出的不是钱，是"平台工程的重复劳动"。** 团队越小、"抽象层摩擦"越贵（饥荒、星露谷）；团队越大、"平台工程重复劳动"越可摊薄（MC）。

## 2. 资源与构建管线

### 2.1 一张总表

| 维度 | Minecraft | 星露谷 | 泰拉瑞亚 | 饥荒 / DST |
|---|---|---|---|---|
| 资源容器 | 无统一容器（散文件 / zip 资源包） | XNB（Content Pipeline 产物） | XNB | `.tex` + `anim.bin`/`build.bin` + 图集 `.xml` |
| 管线时点 | **运行时加载** | **构建期转换** | **构建期转换** | **构建期转换**（Flash 导出 / 工具打包） |
| 内容层格式 | JSON（`.mcmeta`、模型、blockstate、数据包） | JSON（1.6 起大量数据迁到 `Data/`）+ XNB 资产 | 多数硬编码 + 数据表 | Lua 脚本即内容 |
| 覆盖/替换机制 | 资源包、数据包按 pack 优先级覆盖 | 内容包（Content Patcher）+ SMAPI 内容 API 运行时替换 | 1.4 Texture Pack：zip 内 png 优先，缺失回落 xnb | Mod 覆盖脚本 + 替换 build/anim/tex |
| 版本号机制 | `pack.mcmeta` 的 `pack_format`（资源包/数据包各自演进） | manifest / API 版本 | 文件头版本号（存档）；资源包无统一 schema | `api_version`（modinfo） |

### 2.2 分水岭：构建期转换 vs 运行时加载

这是本章唯一需要记住的一条线。

**构建期转换（XNB、anim.bin/build.bin）**

- 收益：运行时零解码成本（纹理数据可直接上传 GPU）、GPU 原生压缩格式（DXT1 4bit/像素、DXT5 8bit/像素）、平台差异提前处理、类型安全（`ContentManager.Load<Texture2D>` 自带 reader 信息）。【社区+推断】
- 代价：**改一个像素要重新走管线**。玩家改素材必须先转格式——这就是"Terraria 改贴图要先 xnb↔png"和"星露谷改图要 StardewXnbHack/xnbcli"的技术根源。【可查】
- 星露谷 1.6 的地图/事件迁移仍是"源文件进管线、运行时读 XNB"，所以 mod 侧必须靠 **Content Patcher 这类框架**在运行时替换，等于在构建期管线上补一层运行时覆盖。【官方+社区】

**运行时加载（MC 资源包/数据包）**

- 收益：改完即生效（`/reload`），资源包/数据包作者可以秒级迭代；社区产能极高。【官方+社区】
- 代价：启动/加载时的解析成本、需要 schema 版本管理、`pack_format` 每次都要跟版本跑。【官方】
- 副作用：`recipe` / `recipes`、`loot_table` / `loot_tables` 这种单复数在版本间改过，是新手最容易踩的坑。【社区】

> **【对照推断】这条分野直接决定了四个社区的性格。**
> - **运行时格式（MC）→ "轻资产、快迭代"的社区**：一个人一天能做出可见的资源包，所以生态基数最大，但也最容易碎片化（同一功能十个包）。
> - **构建期格式（泰拉瑞亚、星露谷）→ "工具链依赖"的社区**：必须先有 TConvert / xnbcli / StardewXnbHack / Content Patcher，否则连替换一张图都做不到。工具链成熟度成了生态天花板。
> - **脚本即内容（DST）→ "逻辑型"社区**：不需要碰资源管线就能改玩法，所以小 mod 门槛最低，但美术类 mod 反而要啃 `.tex`/`anim.bin` 这套私有格式。

### 2.3 XNB 的两套 reader 体系（星露谷 vs 泰拉瑞亚）

XNB 不是"加密压缩包"，而是**带类型信息的 .NET 对象序列化流**：

```text
偏移 0   "XNB"           3 字节魔数
偏移 3   platform        1 字节（w/x/m …）
偏移 4   format version  1 字节
偏移 5   flags           1 字节（0x80 压缩、0x40 HiDef）
偏移 6   total size      4 字节
之后     type reader 数量 + reader 类型名表
         shared resource 数量
         主对象数据（按 reader 规则序列化）
```

社区工具解包时会保留一个 `readers` 数组，里面是程序集限定的类型名（如 `Microsoft.Xna.Framework.Content.DictionaryReader...`），这正好证明 XNB = 类型化对象图。【社区】

> **【对照推断】"MonoGame vs XNA 两个 reader 体系"这件事，在四份源文档里没有被直接展开，只能这样谨慎表述：**
> XNA 4.0 与 MonoGame 虽同源，但 Content Pipeline 是各自独立实现，XNB 头里记录的是 **reader 类型名 + 程序集限定名**。星露谷 Windows 主分支在 2021 年从 XNA 迁到 MonoGame，意味着同一批资源要被新的 reader 注册表解析——这就是"两套 reader 体系"的实际含义。
> 源文档没有披露迁移期如何处理 reader 差异，因此**具体做法【存疑】**；能确定的只有"类型化对象图 + reader 名称内嵌"这个结构本身。【社区】
>
> 对照之下，**泰拉瑞亚没有这个问题**：它一直沿用 XNA Content Pipeline 的产物，而 FNA 是 XNA 4.0 API 的重实现，XNB 读取路径得以延续——这也是为什么泰拉瑞亚不需要像星露谷那样做一次"运行时换代"。【对照推断，源文档只说明 FNA 是 API 重实现与 XNB 是标准产物】

### 2.4 tModLoader 的 patch：一种"构建期的 mod 机制"

tModLoader 的注入方式不是运行时，而是**构建期把 `.patch` 打到反编译源码上**，产出"带钩子的 Terraria"。【可查（仓库结构）】

```text
tModLoader
├─ Terraria 源码（反编译 + 官方授权）
│   └─ 通过 .patch 文件注入 Hook 点（Setup 工程在构建时应用）
├─ Terraria.ModLoader（ModItem / ModNPC / ModTile / ... + xxxLoader 钩子链）
├─ 资源加载（贴图/音效/本地化 .hjson）
└─ Mod 编译与打包（.tmod，zip：build.txt + dll + Content/ + Localization/）
```

关键点：

- **两级 Hook**：① 虚方法/接口钩子（`ModItem.UseItem`），属于官方预留扩展点；② IL/On Hook（MonoMod 系 HookGen），可对任意 vanilla 方法做 `On.Terraria.NPC.Update += ...`，这是兼容性风险的主要来源。【可查】
- **为什么必须官方化**：没有 Re-Logic 授权，维护一份反编译分支在法律上站不住；授权后才敢长期跟版本。【官方+推断】

> **【对照推断】这解释了泰拉瑞亚社区一个常见误解："tModLoader 是运行时注入"是错的。**
> 它和 Mixin（运行时字节码注入）、SMAPI/Harmony（运行时 IL 补丁）不是一类东西。**构建期应用补丁的好处是可被 CI 验证、可跟着大版本重建；坏处是每次大版本都要重做补丁**——这也解释了 1.4 改动巨大后，tModLoader 1.4 分支为什么要数年才稳定。【可查+推断】

### 2.5 Flash 导出 + 自研动画格式（DST）

- **【官方】** 单机时期，美术主要在 **Flash** 中绘制，再导出到自研动画格式。
- **【推断】** 动画 zip 里通常包含 `anim.bin`（时间轴、部件变换、帧事件）、`build.bin`（图集布局、部件与贴图映射、层级）、`atlas-0.tex`（纹理）。社区工具 `krane` 可把 `anim.bin/build.bin` 反编译成 Spriter 工程 `.scml`，`ktech` 做 `.tex`↔PNG 互转，`stex` 打包图集。
- **【存疑】** DST 时代官方美术内部是否全面迁移到 Spriter，没有公开说明。能确定的是：**运行时消费的是编译后的动画包，不是运行时直接读 `.scml`**。【推断】
- 这套管线还承载**帧事件**：脚步、攻击命中、采集判定、音效触发。逻辑层 StateGraph 切状态时播对应动画，动画在特定帧回调事件驱动伤害判定。【推断】——优点是音画同步、手感扎实；缺点是逻辑与美术资源耦合，改动画可能改出 bug。

> **【对照推断】** 于是四家的"资源管线"形成一条清晰的谱：
> **MC（运行时 JSON，改完即生效）→ 星露谷（构建期 XNB + 运行时内容包覆盖）→ 泰拉瑞亚（构建期 XNB + zip 覆盖）→ DST（构建期私有动画包 + 脚本层覆盖）。**
> 越往右，**"改美术"越难、"改逻辑"越容易**。这不是巧合：资源格式越私有，逻辑层就必须越开放来补偿（DST 的 Lua 源码全公开，正是这个补偿）。

## 3. 世界结构

### 3.1 一张总表

| 维度 | Minecraft | 星露谷 | 泰拉瑞亚 | 饥荒 / DST |
|---|---|---|---|---|
| 世界模型 | 无限、按 chunk 流式加载 | 手工地图 + 数据表（有限、小型） | 有限固定尺寸、一次性预生成 | 有限、预生成、分 shard |
| 生成方式 | 三维噪声 + 密度函数 + 群系参数网格 | 预制地图（Tiled `.tbin`）+ 图块属性 + 事件脚本 | 高度图→洞穴噪声→矿石→群系→结构→微调（重算法离线跑） | Level → Task → Room 分层图 + 锁与钥匙 |
| 种子确定性 | 同版本 + 同设置 + 同游戏逻辑成立；跨版本/跨平台不成立 | 不适用（地图手工） | 世界生成可复现（一次性计算） | 种子决定宏观布局；资源刷新/生物/掉落/天气用运行时随机 |
| 存档格式 | 按区块增量写（区域文件） | 未压缩 XML 文本（大型存档可达 15–30MB）【社区】 | `.wld`/`.plr` 二进制 + 文件头版本号 + 瓦片 RLE【推断/可查】 | 世界持久化 + 多 shard 存档 |
| 联机拓扑 | 客户端-服务端；单人 = 内置服务器 | 主机权威（host-authoritative），最多 4 人 | 星形 TCP，主机即服务端，默认端口 7777 | 服务器权威 + 客户端预测 + Master/Caves 双 shard |

### 3.2 世界模型 → 存档格式

| 世界模型 | 存档的天然形态 | 后果 |
|---|---|---|
| 无限流式（MC） | 按区块增量写、可增长的稀疏结构 | 存档随探索边界增长；未探索区域不占空间；区块可独立并行生成（输入只有种子 + 坐标） |
| 有限预生成（泰拉瑞亚） | 固定尺寸稠密表，一次写完，RLE 压缩 + 版本号 | 存档大小可预测；世界生成可以离线用重算法；"进服读条"由此而来 |
| 手工地图 + 数据表（星露谷） | 小规模对象图（玩家/世界/地块状态），XML 文本 | 存的是"状态与变化量"，不是"地形本身"；可读、可手改、可被 mod 解析 |
| 分片持久世界（DST） | 每个 shard 一份存档，世界服务器关了还在 | 存档不是"一次会话"，是"一个长期存在的世界"；重开的语义被改写 |

> **【对照推断】存档格式不是技术选型的自由项，而是世界模型的函数。**
> 只要世界是"无限且按需生成"的，存档就**必须**是可增长的稀疏结构（否则玩家走两万格后存档爆炸）；只要世界是"一次生成完的稠密表"，存档就**最自然**是带版本号的 RLE 块（否则读档要重建整个世界）。
> 这条推论有一个可验证的旁证：MC 的单人游戏跑的是真正的内置服务器（IntegratedServer），所以它连"单人存取"都走的是网络同构路径；而泰拉瑞亚单人是"同一进程内 NetMode 切换"。两者的存档粒度差异，正是这两种拓扑的直接投影。【对照推断，源文档分别给出台阶事实】

### 3.3 世界模型 → 联机难度

| 需要同步的东西 | 谁属于这一类 | 为什么 |
|---|---|---|
| 附近区块 | Minecraft | 无限世界，只能同步"玩家周围"；天然适合增量，但区块生成要保证两端一致 |
| 世界段（一次性全量）+ 图块增量 | 泰拉瑞亚 | 有限世界，进服必须先把 200×150 的区块段发完，所以"读条主要在这里"【推断+可查】 |
| 实体状态（NPC 日程、作物、天气） | 星露谷 | 地图在两端都有，同步的是"当前状态"；难点是 NPC 日程与事件在多人间保持一致 |
| 实体字段（NetVar）+ 请求（RPC）+ 只读镜像（Replica） | DST | 服务器权威，客户端只发请求；UI 读 Replica 而非服务器组件 |

> **【对照推断】结论可以压缩成一句：世界模型决定"同步的单位"。**
> MC 同步**区块**，泰拉瑞亚同步**世界段 + 图块增量**，星露谷同步**状态对象**，DST 同步**实体字段**。
> 四种同步单位对应四种主要故障：MC 是"区块不一致/回弹"，泰拉瑞亚是"进服慢 + 带宽峰值"，星露谷是"NPC 日程错位"，DST 是"你看到的和服务器不一样"。
>
> 还有一个反直觉点：**泰拉瑞亚的"有限世界"反而让联机更难起步**。无限世界可以"走到哪同步到哪"，有限世界必须在进服时把一张完整的表交出去——这就是为什么它要做分段下发和瓦片压缩。

### 3.4 世界模型 → mod 能力边界

| 游戏 | 世界的本质 | mod 能改到哪一层 | 改不到哪一层 |
|---|---|---|---|
| Minecraft | 算法生成 | 加维度、改生成器（数据包可覆盖 `worldgen/noise_settings`）【官方】 | 改引擎的区块渲染/网络协议（必须靠 Mixin 硬改） |
| 泰拉瑞亚 | 一次生成完的稠密表 | 加图块/物品/NPC/配方/弹幕（ID 体系内追加） | 改变世界结构本身（生成算法在代码里，且新 ID 不能重排） |
| 星露谷 | 手工地图 + 数据表 | 换地图、加事件、改作物/机器/对话（内容包 + 数据层） | 大量行为仍在 C# 里，最终要写代码或打 Harmony 补丁 |
| DST | 脚本生成的图 | 改生成脚本（`tasks/rooms/levels/storygen`）、加 Prefab/角色 | 引擎层；且受 shard 与服务器权威约束 |

> **【对照推断】mod 能力边界 ≙ 世界模型的"可参数化程度"。**
> - MC 的世界由**参数**（噪声、密度函数、群系区间）决定，所以"改参数"就能改世界——数据包能做到，门槛最低、能力最"正统"。
> - 泰拉瑞亚的世界由**算法**一次算完，参数不在外部，所以 mod 只能"往里加东西"，不能"改生成规则"。
> - 星露谷的世界是**资产**，所以 mod 能换资产、加事件，但改不了"生活模拟"的规则。
> - DST 的世界由**脚本**生成，脚本又是公开的，所以 mod 能改生成——但生成结果必须被服务器接受，所以能力被"服务器权威"截断。

## 4. 设计范式对照

### 4.1 一张总表

| 维度 | Minecraft | 泰拉瑞亚 | 星露谷 | 饥荒 / DST |
|---|---|---|---|---|
| 范式 | **系统驱动** | **目标驱动** | **时间预算驱动** | **压力/负反馈驱动** |
| 核心循环 | 打树→工具→挖矿→维度→自动化 | 探索→装备→Boss→新阶段 | 单日预算内四线取舍→结算→下一天 | 采集→建造→压力上升→更远更险 |
| 替代任务链的机制 | 能力质变 + 世界可改造 + 涌现系统（红石/农场） | Boss 当**进度锁**（打→掉材料→造装备→开新层） | 一个硬约束（时间）+ 一个软约束（能量）+ 社区中心软任务网 | 三条资源线耦合 + 季节 deadline + 知识作为元进度 |
| 进度载体 | 玩家资产与建筑 | 角色装备 + 世界状态（硬模式改写地图规则） | 金钱/工具/好感/收集 + 农场规模 | 玩家知识 + 基地 + 角色 |
| 失败成本 | 低（掉物品、5 分钟找回窗口、床、`/keepInventory`） | 中（掉金钱而非装备，软惩罚） | 极低（无失败状态，只有机会成本） | 高（单机删档；DST 团队成本） |
| 新手劝退点 | "不知道干什么" | 海量物品的选择困难 | 第一年的"穷"与慢热 | 冬天的新手墙 |

### 4.2 各自用什么替代了传统任务链

**Minecraft：用"门"替代"数值"**

- 木镐→石镐不是 +20% 速度，而是"能挖铁"；铁镐→钻石镐是"能挖黑曜石→能进下界→能去末地"。这种"门"比数字清晰，也更容易被玩家自己感知。【官方方向 + 社区】
- 世界可改造 → "想法 = 可实现"，这是沙盒最核心的承诺。
- 红石/刷怪塔/农场是**玩家自己发明的工程问题**：游戏提供规则，玩家提供目标。
- 代价：Mojang 只能用配方书、进度、教程世界来"降低迷路概率"，没有改变"沙盒优先"的取向。【官方+社区观察】

**泰拉瑞亚：用"钥匙"替代"终点"**

- Boss 不是挑战内容，是**进度锁**：击败 → 掉落材料 → 回工作台合成 → 解锁下一层地图/事件。【官方设计意图 + 可查】
- 单一目标消除迷失感："玩家永远知道下一步该打谁"。
- 血肉之墙不是加数值，而是**改地图规则**（硬模式、新矿、腐化/神圣蔓延），把"重复探索"变成"新探索"。
- 材料即进度：Boss 掉材料而不是终极武器，强迫玩家回到工作台，天然形成"打→造→再打"的节奏。

**星露谷：用"预算"替代"关卡"**

- 一天 6:00–2:00，共 1,200 游戏分钟，现实约 14 分钟；季节 28 天；起始能量 270。【社区】
- 精妙处在于：**只有一个硬约束（时间）和一个软约束（能量），却能让四种完全不同的玩法共享同一套预算。**
- 四条线不是互不相干，而是**正和耦合**：采矿→洒水器/工具→农业规模化；农业→金钱→礼物→社交；社交→配方→加工与收集。真正的冲突只有机会成本，没有失败状态。
- 社区中心把四线编成一张"软任务网"：要求作物/动物产品/矿物/鱼/料理/工匠品，迫使玩家浅尝每个系统，但不规定顺序。

**饥荒：用"deadline"替代"目标"**

- 季节是节奏控制器：默认秋 20 / 冬 15 / 春 20 / 夏 15 天（世界设置可调）。【官方/游戏数据】
- 冬天不是"难度调高"，而是**一次系统性的准备检查**：温度、食物、光照、Boss、信息五重压力叠加。
- 三条资源线的耦合比三条线本身更重要：饥饿→生命是"掉血倒计时"；理智→生命是"影怪 + 判断失误"；黑暗→一击必杀把火把从便利品变成硬性资源。
- 负反馈是**设计出来的**，不是失败惩罚的副产品：基地越大越依赖照明/保暖/防火；探索越远回程成本越高；食物越丰富腐烂管理越复杂。
- 元进度是**知识**：死亡删掉的是存档，不是你的知识。

### 4.3 新手劝退点在哪

| 游戏 | 劝退点 | 本质 | 官方/设计的缓解手段 |
|---|---|---|---|
| Minecraft | 不知道干什么 | 目标由玩家提供，游戏不提供 | 配方书、进度系统、教程世界【官方】 |
| 泰拉瑞亚 | 海量物品的选择困难 | 内容量本身就是门槛 | 职业引导 + 明确掉落来源【推断】 |
| 星露谷 | 第一年穷、节奏慢、无外部目标 | 稀缺是刻意设计的情绪曲线起点 | 无失败状态让玩家可以自由偏科；软任务网提供方向【官方+推断】 |
| 饥荒 | 冬天 | 信息不对称 + 系统性准备检查 | 世界设置可调难度；死亡可归因，下一局更快【官方+推断】 |

> **【对照推断】四种劝退点的性质完全不同，这是四条范式最本质的差异。**
> - MC 的劝退是**动机型**：不是不会玩，是不知道为什么要玩。解法只能是"给短目标"（配方书/进度），治标不治本。
> - 泰拉瑞亚的劝退是**认知型**：目标很清楚，但选项太多。解法是"给路径"（职业引导、掉落来源）。
> - 星露谷的劝退是**节奏型**：一切都很清楚，就是慢。解法是"取消失败状态"——反正不会输，慢慢来也行。
> - 饥荒的劝退是**知识型**：目标清楚、节奏清楚，就是不知道冬天会来。解法是"让失败可归因"——死一次就学会了。
> **一句话：MC 缺目标、泰拉瑞亚缺路径、星露谷缺耐心、饥荒缺信息。**

### 4.4 驱动力光谱

> **【对照推断】** 把四种范式排成一条谱，会看到一个整齐的对应关系：

```text
系统驱动 ──────── 目标驱动 ──────── 预算驱动 ──────── 压力驱动
（无目标）        （强目标）        （软目标）        （反向目标）
引导最弱          引导最强          引导中等          引导反直觉
Minecraft        泰拉瑞亚          星露谷            饥荒
```

- **引导强度与"玩家自主度"成反比**：泰拉瑞亚最"知道下一步"，代价是最像关卡线；MC 最自由，代价是最容易迷路。
- **正反馈 vs 负反馈**：泰拉瑞亚和饥荒都"永远知道下一步"，但泰拉瑞亚是"变强了去打下一个"，饥荒是"别死，撑过下一季"。同样是强引导，一个拉、一个推。
- 星露谷是唯一"既没有强目标也没有死亡威胁"的一款，它靠"预算"这个中性约束把玩家留在循环里——这也是它最容易被误判为"没有设计"的原因。

## 5. 内容量策略

### 5.1 四种机制

| 机制 | 谁在用 | 具体做法 | 解决什么问题 |
|---|---|---|---|
| **数据定义 vs 运行时对象** | 四家都用 | MC：方块状态/配方/战利品表是 JSON；泰拉瑞亚：数千 ItemID 是数据定义，只在需要时实例化；星露谷：1.6 把大量硬编码事件迁到 `Data/`；DST：Prefab 是声明式定义 | 让"内容量"与"运行时开销"解耦——几千件物品不等于几千个对象 |
| **分层淘汰** | 泰拉瑞亚最典型；MC 用变体 | 泰拉瑞亚每个阶段只有一条主材料线，旧装备自然淘汰，不做跨层平衡；MC 用"能力质变"代替数值，所以压根不需要平衡大量数值 | 避免"5000 件物品调成同一强度"的不可能任务 |
| **正和耦合** | 星露谷最典型；MC 有旁支 | 星露谷四线互为输入；MC 的附魔/红石/酿造/村民反向加速主线 | 让多条线共存而不互斥，冲突只剩机会成本 |
| **角色重做** | DST | 重做改变玩法而不只是强度，同时带动动画/音效/台词/皮肤/平衡，是一次内容复用 | 长线运营下的"低成本高讨论度"产出 |

泰拉瑞亚的分层淘汰值得单独说，因为它是"内容量管理"最干净的样本：

- **单一主材料线**：铜/铁/银/金 → 魔矿/狱石 → 神圣锭 → 叶绿/蘑菇锭……设计者只需保证"当前层内部有几个可选流派"。【可查】
- **掉落表做长尾**：稀有物品低概率掉落制造"刷"的动力，同时提供替代路径（合成、NPC 出售、事件奖励）；1.4 之后加入运气值与微光（Shimmer）转化，本质是给 RNG 加保底与转换通道。【官方】
- **稀有度颜色做信息压缩**：白/蓝/绿/橙/红/青/紫/粉，玩家一眼判断价值，不需要读数值。【可查】
- **代价**：后期物品同质化（大量"某职业的又一把剑"）+ 新玩家选择困难。Terraria 用"职业引导 + 明确掉落来源"缓解。【推断】

### 5.2 为什么四家的"更新方式"长得完全不一样

| 游戏 | 进度结构 | 天然产出的更新形态 | 例子 |
|---|---|---|---|
| Minecraft | 系统沙盒（无主线） | **水平**：加系统/生物/维度 | 红石、下界、深暗 |
| 泰拉瑞亚 | Boss 闸门（线性分层） | **垂直**：加层/加 Boss/加物品 | 硬模式、月亮领主 |
| 星露谷 | 时间预算 + 正和耦合 | **生活内容 + 系统深度 + QoL** | 1.5 姜岛、1.6 数据层重构 |
| 饥荒 / DST | 压力 + 季节 | **内容弧 + 角色重做 + 皮肤变现** | Return of Them、From Beyond、2019 起角色重做【官方】 |

> **【对照推断】这是一条很少被说破的因果：更新方式不是"团队喜好"，而是"进度结构的必然产物"。**
> - 进度结构如果是**线性闸门**（泰拉瑞亚），新内容最自然的形态就是"在链条末端再加一环"——所以它只能垂直加。
> - 进度结构如果是**系统沙盒**（MC），没有"末端"，只能往"系统维度"上扩——所以它只能水平加。
> - 进度结构如果是**预算型生活模拟**（星露谷），没有"层"也没有"系统维度"，只能往"更多可做的事"上加。
> - 进度结构如果是**压力型生存**（DST），压力来自"环境"，所以新内容最自然是"新的环境威胁 + 新的应对角色"。
>
> 反过来说，**一个游戏想做某种更新，就得先有对应的进度结构**——这解释了很多"缝合怪"为什么缝合失败：把线性闸门塞进沙盒，两边都不成立。

### 5.3 内容量与运行时开销的解耦

四家在这件事上手法不同，但目标一致：

| 游戏 | 手法 | 量化体现 |
|---|---|---|
| 泰拉瑞亚 | 固定大小预分配数组 + 槽位复用 + `active` 标志；物品是数据定义，只有背包/掉落物是实体 | 零 GC 压力、遍历成本可预测、槽位索引天然是网络 ID 的一部分【推断+可查】 |
| Minecraft | 区块/实体/粒子的批量提交；性能模组第一件事是"少分配"而不是"少计算" | GC 停顿直接表现为卡顿【社区】 |
| 星露谷 | 数据表 + 图集 + 对象图存档；性能瓶颈是内容量与逻辑复杂度，不是语言速度 | 16×16 地块、几百实体，C# 够用【访谈+推断】 |
| 饥荒 | 引擎 C++ 承担渲染/动画/网络，Lua 只承担玩法；官方必须持续"盯性能" | 解释执行 + 频繁小对象分配，实体一多就撞 GC 和 CPU【官方+推断】 |

> **【对照推断】** 值得注意的分歧：**泰拉瑞亚用"上限"换确定性，MC 用"批量"换吞吐，星露谷用"规模小"回避问题，饥荒用"分层"把性能压力推给 C++。**
> 四条路都成立，因为它们服务的目标不同：泰拉瑞亚要"战斗手感不能打折"，MC 要"无限世界不卡"，星露谷要"内容多但实体少"，饥荒要"玩法迭代快"。

## 6. 美术与音乐路线

### 6.1 美术总表

| 维度 | Minecraft | 星露谷 | 泰拉瑞亚 | 饥荒 / DST |
|---|---|---|---|---|
| 基本单位 | 16×16 方块贴图（风格默认，非引擎限制）【官方】 | 16×16 地块 / 16×32 角色 / 64×64 立绘 | 16×16 图块；玩家帧 40×56 级别 | 手绘部件 + 剪纸骨骼 |
| 渲染缩放 | 任意分辨率资源包均可 | 4× 整数缩放 | 整数倍 + 最近邻采样 | 手绘可缩放 |
| 动画方式 | 方块模型 JSON；生物动画是代码里的关键帧【社区】 | 4 方向 × 4 帧行走 + 立绘表情 | 图集邻接变体（自动拼接）+ 分层换装 | `anim.bin`/`build.bin` 部件化骨骼动画 |
| 风格维护手段 | 同批人 + 同栅格 + 同调色习惯；1.14 Jappa 重制【官方】 | 固定尺寸契约 + 固定 3–5 级色阶 + 模板复用 + 季节换皮 | 1px 描边 + 统一受光 + 色相分层 + 图集化 + 重绘旧素材 | 剪影优先 + 粗黑描边 + 低饱和大地色 + 高饱和危险色 |
| 可替换性 | 资源包可全量替换 | 内容包可替换 | 1.4 Texture Pack 可替换 | Mod 可替换 build/anim/tex |

### 6.2 三种像素约束系统（MC / 星露谷 / 泰拉瑞亚）

三家都是 16×16 起步，但"怎么维持一致性"用的是三套完全不同的约束：

| 游戏 | 约束维度 | 具体规则 |
|---|---|---|
| Minecraft | **调色板与明度** | 每块 4–8 色；明度阶梯优先于色相跳跃；三面区分（顶亮/侧中/底暗）；类别色锚点（石=灰、木=棕、金属=冷灰+高光、矿物=石底+彩色斑点）；避免高频细节；轮廓靠"边"【社区/美术经验】 |
| 星露谷 | **尺寸与模板** | 所有角色 16×32、所有立绘 64×64、所有地块 16×16；同一材质固定 3–5 级色阶；模板复用（身体/发型/服装/地块边缘/建筑部件）；季节变体而非重画一切【社区+访谈】 |
| 泰拉瑞亚 | **描边与受光** | 1px 深色描边保证剪影分离；统一受光（高光左上、阴影右下）；层级用色相区分（铜橙→铁灰→银白→金黄→魔矿紫→狱石橙红→神圣粉白→叶绿翠绿）；Boss 用尺寸做威胁提示【可查+推断】 |

> **【对照推断】这三套系统验证了同一条结论：像素风格的一致性来自"限制系统"，不是"画功"。**
> 但三者限制的维度不同，所以"崩坏方式"也不同：
> - MC 限制**明度**，所以最常见的失败是"色相跳变过大（远看是花的）"和"细节密度过高（远看是灰的）"。
> - 星露谷限制**尺寸**，所以最常见的失败是"尺寸不统一导致网格压不平"（一个 24×24 的角色放进 16×16 的网格就立刻出戏）。
> - 泰拉瑞亚限制**描边与受光**，所以最常见的失败是"忘记给新图块配 merge 规则导致接缝"。
>
> 一句话：**MC 的规范在"颜色"里，星露谷的规范在"网格"里，泰拉瑞亚的规范在"轮廓"里。**

### 6.3 剪纸骨骼 vs 像素逐帧

| 维度 | 骨骼/剪纸（饥荒） | 逐帧/像素（MC、星露谷、泰拉瑞亚） |
|---|---|---|
| 资源体积 | 小（部件 + 曲线） | 大（每帧一张图） |
| 复用 | 高（换贴图/换骨架） | 低 |
| 变形能力 | 有限（部件刚性变换） | 强（可自由变形，但成本高） |
| 风格适配 | 剪纸、木偶、机械 | 流畅写实、像素 |
| Mod 友好 | 高（可替换 build/anim） | 低（改一帧要重走管线） |
| 商业价值 | 换装/皮肤建立在同一套骨骼与图集之上 | 换装就是重画 |

> **【对照推断】饥荒选剪纸骨骼，不只是"风格选择"，更是"产能选择"和"商业模式选择"。**
> 手绘部件 + 骨骼意味着：一套骨架换贴图就是新皮肤——这直接支撑了 DST 的皮肤变现（见 §7）。像素逐帧做不到这一点，所以 MC / 星露谷 / 泰拉瑞亚的"外观商业化"只能靠"换整套模型/贴图"，成本高得多。
> 而"僵硬感"在饥荒里不是缺陷，是风格的一部分：角色像被线牵着的木偶，动作有轻微顿挫，配合低帧率关键帧形成荒诞感。【推断】

### 6.4 音乐生产方式对照

| 游戏 | 作曲 | 生产方式 | 运行时策略 | 格式 |
|---|---|---|---|---|
| Minecraft | C418 奠基；后 Lena Raine、Kumi Tanioka、Aaron Cherof 等接力【官方】 | 极简动机 + 长发展；大量留白；电子音色 + 钢琴；不追求主题曲式记忆点，追求"挖矿时不烦" | 客户端音乐调度器**随机间隔触发**（约 10–20 分钟量级，具体 tick【待考】），按维度/环境分组；洞穴环境音是另一套机制 | OGG Vorbis；`sounds.json` 多文件随机 + 权重 + `stream`；**单声道才空间化** |

### 6.5 音乐与玩法是什么关系

四家的音乐"服务对象"完全不同，这是最值得对照的一点：

- **MC：陪伴，不抢戏。** 低频、慢速、不推动、不叙事。这条隐形规则让多作曲者接力后听起来仍是一个游戏。【推断】
- **星露谷：先有音乐，后有场景。** 作者自称 work flow 是"先做音乐，再根据音乐去做场景与动画"，所以很多地图情绪和曲子情绪高度贴合。【访谈】
- **泰拉瑞亚：用音乐标记"你在哪"。** 主题 + 变奏，用配器告诉你"这是雪原/地狱/地牢"，Boss 音乐用铜管 + 急促打击强调"战斗开始"。【推断】
- **DST：用音乐制造压力。** 状态驱动 + 静默；紧张感不只靠音乐，还靠"夜晚/洞穴/低理智时环境音骤减"、心跳/呼吸、Boss 远处吼叫。【推断】

> **【对照推断】音乐的生产方式与团队规模强相关，而"音乐与玩法的关系"与设计范式强相关。**
> - 规模：一人项目（星露谷）必然选"风格统一但产量有限"；三人小组（DST）可以分工做状态化分层音乐；长期单一作曲者（泰拉瑞亚的 Scott）能保证主题连贯；MC 则靠"不抢戏"这条规则让多人接力仍然统一。
> - 范式：系统驱动（MC）要"陪伴"、目标驱动（泰拉瑞亚）要"标记地点"、预算驱动（星露谷）要"标记季节与时刻"、压力驱动（DST）要"制造不安"。
> **换句话说：音乐不是"配乐"，是范式的听觉投影。**

### 7.2 规模决定"能不能重写"

> **【对照推断】这一章最实用的一条推论：团队规模直接决定"哪些工程手段是可选项"。**

| 团队规模 | 能做什么 | 不能做什么 | 对应案例 |
|---|---|---|---|
| 1 人 | 冻结架构、只换运行时、靠外部协助完成联机 | 重写引擎、同时维护双运行时 | 星露谷拖了五年才从 XNA 迁到 MonoGame |
| 个位数到十几人 | 持续小版本、慢慢加内容、构建期补丁 | 停更两三年重写引擎 | 泰拉瑞亚不换 Unity |
| 数十人 | 承受一次大渲染重写（1.17 的 OpenGL 3.2）、高频快照集成 | 放弃 mod 生态 | Minecraft |
| 六七人核心 | 自研工具链做到极致贴合、靠 Lua 分层换迭代速度 | 通用工具、招聘池、平台工程摊薄 | 饥荒 |

一句话：**"要不要自研/要不要重写"不是技术判断，是团队规模判断。**

### 7.3 存档兼容压力的三条不同解法

| 游戏 | 策略 | 具体做法 | 边界 |
|---|---|---|---|
| 泰拉瑞亚 | **硬扛 15 年** | 文件头版本号 + 只追加不删 ID + 废弃内容软删除 + 默认值补齐 + `.bak` 与云存档 + 世界升级而非重生成【可查+官方】 | 代价是 ID 空间只增不减，世界结构无法重排 |
| 星露谷 | **迁移 + 兜底** | 宽容反序列化 + 加载时迁移 + 备份恢复 + 尽量不删旧 ID【社区+官方】 | 1.6 改 ID/统计/farmhand 结构需单向迁移；**1.6.9 存档不能再在 1.6.8 加载**【官方】 |
| Minecraft | **把压力外移给 mod 生态** | "同种子同世界"只承诺"同版本 + 同设置 + 同逻辑"；跨版本/跨平台不保证【官方】 | 每次大版本 mod 都要重做，压力由社区承担 |
| DST | **换成"持久世界 + 分片"** | 世界持久化；Master/Caves 各自独立端口、配置、Mod 列表、存档【官方/推断】 | 跨 shard 一致性要额外处理；Mod 版本不一致进不去服务器 |

> **【对照推断】把四家的兼容策略放在一起，会看到一条清晰的权衡：**
> **兼容压力 ≈ 内容累积年数 × 更新频率 ÷ 可外移程度。**
> - 泰拉瑞亚：年数极长、频率低、可外移程度低 → 只能硬扛，所以它把"只追加 ID"做成了铁律。
> - 星露谷：年数中等、频率低、可外移程度中 → 用"迁移 + 备份 + 降级警告"软扛。
> - MC：年数极长、频率极高、可外移程度高 → 直接把压力外移给 mod 生态（代价是 mod 作者长期疲惫）。
> - DST：年数中等、频率高、可外移程度高 → 用"持久世界 + 分片"把压力转移到运维和 Mod 一致性上。

## 8. mod 生态的技术前提

### 8.1 一张总表

| 维度 | Minecraft（Fabric/NeoForge） | 星露谷（SMAPI/Harmony） | 泰拉瑞亚（tModLoader） | 饥荒 / DST |
|---|---|---|---|---|
| 机制 | **Mixin 字节码注入** + 事件总线/补丁 | **IL 补丁**（Prefix/Postfix/Transpiler）+ 内容 API | **授权源码分支 + `.patch` 构建期应用** + 两级 Hook | **Lua 运行时注入**（setfenv 沙箱 + PostInit 钩子） |
| 前置 | 反编译 + 映射（Yarn/Mojmap）+ Gradle | 反编译可读（未混淆）+ C# | C# 面向对象 + 理解原版代码 | 无需编译；官方 Lua 源码随游戏发布 |
| 门槛 | 中高 | 中 | 中 | **低**（小 mod） |
| 能力上限 | 最强（可改任意方法/字段） | 强（可改任意方法 IL） | 最强（等价于改源码） | 中（只能在钩子点插入，受 Lua 性能限制） |
| 版本脆弱性 | 高（快照期就可能改内部结构） | 中（未混淆 + SMAPI 兼容层兜底） | 低-中（补丁式可重建，但 1.4 改动大导致重做数年） | 高（API 不稳定，版本更新常破坏 mod） |
| 分发 | CurseForge / Modrinth 等 | Nexus / 官方论坛 | Steam DLC + Workshop | Steam 创意工坊一键订阅 |

### 8.2 侵入性光谱

> **【对照推断】把四种机制按"侵入程度"排列，会得到一条非常好用的光谱——每一级都是"能力换稳定性/合法性"：**

```text
数据覆盖                    脚本注入                  IL/字节码补丁              源码分支
（不改代码）                （不改引擎）              （运行时改方法）           （构建期改一切）
MC 数据包/资源包            DST Lua 钩子              SMAPI/Harmony、Mixin      tModLoader
星露谷 Content Patcher
──── 最稳、能力最弱 ────────────────────────────────────────────► 最强、最不稳/最依赖授权
```

光谱每一级的工程含义：

| 层级 | 改什么 | 稳定性来源 | 典型失效方式 |
|---|---|---|---|
| 数据覆盖 | 只改数据/资产 | 游戏本身不改 | 游戏 schema 变了（`pack_format` / 数据目录单复数） |
| 脚本注入 | 在钩子点插入逻辑 | 钩子 API 稳定 | API 改名/钩子点消失 |
| IL/字节码补丁 | 任意方法任意注入点 | 注入点选择正确 | 注入点被上游重构（Mixin 的经典死法） |
| 源码分支 | 一切 | 补丁可被 CI 验证 | 官方大版本改动导致补丁大面积冲突 |

### 8.3 门槛最低 vs 能力最强

**门槛最低：DST。**

- 语言 Lua，无需编译；官方玩法层源码放在 `scripts.zip` 里，随游戏发布；创意工坊一键订阅。【官方+推断】
- 最小 mod 只要 `modinfo.lua` + `modmain.lua`，用 `AddPrefabPostInit` / `AddComponentPostInit` 这类钩子就能改行为。【推断】
- 但注意源文档的一个关键限定：**"门槛低"指小 mod，不指大型 overhaul。** 动态类型 + 全局钩子会让大型 Mod 互相踩，调试工具也不如成熟 IDE 生态。【推断】

**能力最强：要区分两个维度。**

| 候选 | 改造深度 | 稳定性/合法性 |
|---|---|---|
| Mixin（MC） | 最强：任意方法任意注入点 | 最差：依赖反编译研究，每次快照可能失效；且不允许分发本体的反编译源码【官方 EULA 精神】 |
| tModLoader（泰拉瑞亚） | 最强：等价于改源码 | 最好：有官方授权 + 构建期补丁可 CI 验证 |

> **【对照推断】所以"哪种能力最强"其实有两个答案，取决于你问的是"能改多深"还是"能改多久"。**
> - 论**单次改造深度**：Mixin 与 tModLoader 并列第一。Mixin 不需要源码分支，理论上可以注入任何地方；tModLoader 直接就是源码。
> - 论**可持续能力**：tModLoader 明显更强——因为它把"修改"变成了"构建期补丁"，可以被 CI 验证、可以跟着大版本重建；Mixin 的注入点在每次上游重构后都可能消失。
> - 一句话：**Mixin 是"外科手术"，tModLoader 是"拿到病历本再动刀"。**

### 8.4 技术前提是必要非充分

> **【对照推断】一个反直觉的观察：mod 生态的规模不完全由技术门槛决定。**

| 游戏 | 门槛 | 生态规模 | 为什么 |
|---|---|---|---|
| MC | 中高 | 最大 | 运行时数据格式 + 官方映射 + 生态分裂（Forge/Fabric/NeoForge）反而催生多个社区；"加内容"的需求天然巨大 |
| DST | 最低 | 中等 | 玩法层简单、上限受 Lua 限制、长线内容主要靠官方产出；但"改规则"的需求很集中 |
| 泰拉瑞亚 | 中 | 大（Calamity/Thorium 等） | 内容量巨大且"加 Boss/加物品"是最自然的需求；tModLoader 官方化 + Workshop 分发 |
| 星露谷 | 中 | 大且长尾 | 未混淆 + 数据驱动 + SMAPI/Harmony + 框架层（Content Patcher / SpaceCore / FTM）让"组合"成为可能 |

> **【对照推断】** 所以完整公式是：
> **生态规模 = 技术门槛的可及性 × 内容需求 × 分发渠道 × 官方态度。**
> - MC 门槛不低，但"内容需求"与"官方态度（默许）"都极高。
> - DST 门槛最低，但"内容需求"集中于改规则，"官方内容供给"又很足，所以生态规模被压制。
> - 泰拉瑞亚与星露谷靠"官方化/官方容忍 + 现成框架层"把门槛压到可接受，再叠加巨大的内容需求，才长成大型生态。

## 9. 如果要自己动手：三条可执行路线

> 三条路线都来自源文档的"动手项目"，按"难度递增"重新编排。
> 每条路线的项目**可独立验收、可回退**，前一个不是后一个的硬前置（除非注明）。

### 9.1 先选路线：它们训练的是三种不同的能力

| 路线 | 难度起点 | 主要训练 | 适合的终点 |
|---|---|---|---|
| A. 2D 格子向 | 低 | 数据布局、渲染、光照、网络同步 | 想做 2D 沙盒/动作游戏的人 |
| B. 内容驱动向 | 低-中 | 内容管线、数据建模、存档迁移 | 想做"内容量大、系统多"的游戏的人 |
| C. 脚本引擎向 | 中（但天花板最高） | 运行时注入、状态机、服务端/客户端边界 | 想做"玩法迭代快、mod 生态"的游戏的人 |

> **【对照推断】建议按"你想要的终点"选路线，而不是按"起点难度"选。**
> A 的终点是"引擎能力"，B 的终点是"内容产能"，C 的终点是"架构与生态"。三者不互斥，但一个人很难同时练满。

### 9.2 路线 A：2D 格子向

**A1｜复刻 2D 网格光照（1–2 天）**

- 建 2D 网格并标记"是否阻挡光"；每帧：清空光照缓冲（彩色 + 白色两张）→ 光源写能量 → 4 邻域迭代衰减传播 → 水平/垂直两次模糊 → 与场景乘法混合。
- 加入两种光（`color` 与 `white`），对比"只有白光"与"彩色光"的观感差异。
- 验收：墙角不漏光、火把有颜色、30×30 网格 60 FPS 无压力。
- 学到：网格传播、屏幕空间模糊、两种光的合成逻辑。

**A2｜瓦片世界 + 自动拼接 + 二进制存档（1–2 周）**

- 位掩码实现 16 种基础邻接变体，再扩展到斜坡/半砖；给图块配 merge 规则。
- 用 RLE 压缩瓦片存档，写版本号与迁移函数。
- 加视口裁剪渲染，大世界（如 4000×1200）也能跑。
- 验收：拼接无缝；100 万格存档秒级完成；裁剪后帧率稳定。

**A3｜多阶段 Boss（1 周）**

- `ModNPC` 式状态机（Idle → AttackA → AttackB → Phase2），计时器切阶段；部位用独立实体 + `realLife` 绑定本体；弹幕编排（扇形/追踪/地火）；血条 UI、出场提示、音乐切换、掉落表。
- 验收：单机能完整打完；阶段切换可读；掉落正确。

**A4｜小型多人同步 Demo（2 周）**

- TCP 长连接 + 自定义二进制消息（消息号 + 长度 + 载荷）；进服分段下发世界（带压缩），之后只发增量；玩家位置同步 + 插值；简单的服务端权威校验（如移动速度上限）。
- 验收：2 个客户端看到彼此平滑移动；断线重连不崩；带宽可控。

> A 线顺序建议：**A1 → A2 → A3 → A4**。理由：先建立"网格"直觉，再建立"数据/存档"直觉，再进"状态机"，最后做网络（网络最能暴露前三步的欠账）。

### 9.3 路线 B：内容驱动向

**B1｜做一个"像样"的资源包 / 内容包（1–2 天）**

- MC 路线：替换 3 个方块贴图 + 给一个方块加动画（`.mcmeta`）+ 用 `parent` 继承修改一个模型。学到 `pack.mcmeta` / `pack_format`、atlas、模型继承、UV 布局、blockstate→模型的映射。
- 或星露谷路线：写一个 Content Patcher 的 `content.json`，替换 NPC 季节立绘或调一种作物的售价/生长天数。学到 `Action: EditImage/Load`、`Target`、`When` 条件、动态 token。
- 验收：游戏能启动、目标资源被替换、卸载后恢复原状、日志无报错。

**B2｜做一个数据包（2–4 天）**

- 自定义配方 + 战利品表 + 进度 + 一个 `.mcfunction` + 一个自定义维度（`worldgen/`）。
- 学到：命名空间、注册表、加载顺序、`/reload` 的边界（有些东西 reload 不生效，必须重启）。
- 验收：`/datapack list` 能看到它，配方在配方书里出现。

**B3｜写第一个 Fabric mod（3–7 天）**

- 注册一个物品 + 一个方块 + 一个创造模式物品栏标签 + 一个简单 `BlockEntity`（比如会缓慢转动的方块）。
- 学到：注册表 API、`Identifier`、客户端/服务端分离（`ClientModInitializer` vs `ModInitializer`）、资源包与代码的配合。
- 验收：能合成、能放置、能存档（退出重进后状态还在）。
- 进阶提示（不计入本条）：项目 4 的 Mixin（`@Inject`/`@Redirect`/`@ModifyVariable`）建议固定一个版本做完，因为它最容易被版本更新打断。

**B4｜复刻"一天"的农场循环（1–2 周）**

- 用 MonoGame（或 Unity/Godot）做一个最小可玩原型：网格农场、时间推进、能量消耗、作物状态机、背包、睡觉结算、JSON 存档。
- 所有数值走配置文件，不改代码就能调。
- 验收：能种下/浇水/收获；2:00 会昏倒；睡觉后作物进入下一阶段；读档后状态一致。

> B 线顺序建议：**B1 → B2 → B3 → B4**。理由：从"只改资产"到"只改数据"到"加代码"到"综合复刻"，每一步都在扩大"我能改到什么"的范围，且都能独立验收。

### 9.4 路线 C：脚本引擎向

**C1｜信息类客户端 Mod（难度：低）**

- 做"显示食物新鲜度/恢复量"的 UI Mod；`modinfo.lua` / `modmain.lua`；客户端 UI；读 Replica（`health`/`hunger`/`sanity`/`perishable`）；`client_only_mod = true`。
- 验收：服务器不需要装、客户端也能用；悬停显示；不改任何服务器状态。
- 学到：客户端/服务器边界、Replica 的只读语义、UI 生命周期。

**C2｜自定义物品 + 配方 + 资源（难度：低-中）**

- 加一把"燧石匕首"：新 Prefab、新配方、新图集（`.tex`/`.xml`）、新动画包（`anim.bin`/`build.bin`）。
- 验收：可合成/可装备/可攻击；物品栏图标、地面模型、手持动画都正确；卸载 Mod 后存档不崩溃。
- 学到：资源管线、Prefab 生命周期、配方系统、服务器端逻辑与客户端表现分离。

**C3｜角色 Mod（难度：中）**

- 基于 ESC 模板：`AddModCharacter`；三属性；`stategraph`、`brain`、台词/语音；角色专属配方；皮肤/ghost 形态。
- 验收：能出生/死亡/复活；被动在服务器端生效、客户端表现正确；主动技能有冷却/消耗/动画/音效；多人测试不出现"只有主机看得到"。
- 学到：角色系统、状态机、服务器/客户端同步、内容量级对架构的影响。

**C4｜复刻"昼夜 + 三条资源线"（难度：中）**

- 用 Godot/Love2D，只复刻核心系统：固定时间步的模拟循环、状态机/组件化、数据驱动调参（JSON/Lua 表）、UI 与模拟分离。
- 验收：一天有明确昼夜阶段；饥饿归零后持续掉血；低理智触发"影怪"事件；所有数值可在配置里调。
- 学到：系统耦合、时间片设计、负反馈循环、可调参架构。

> C 线进阶（不计入本条）：**小型世界生成器**——图结构（节点=Task、边=连接）+ 权重随机 + 锁与钥匙 + 房间模板 + 种子复现，验收标准是"同种子同图、3–5 种可区分群系、至少一个需条件进入的区域"。它是 C4 之后最自然的一步，也是四份源文档里唯一"中-高"难度的项目。

### 9.5 三条路线分别在训练什么（对照表）

| 能力 | A. 2D 格子向 | B. 内容驱动向 | C. 脚本引擎向 |
|---|---|---|---|
| 数据结构与内存布局 | ★★★ | ★ | ★★ |
| 渲染/光照 | ★★★ | ★ | ★ |
| 资源管线 | ★ | ★★★ | ★★ |
| 数据建模与调参 | ★ | ★★★ | ★★ |
| 状态机 | ★★ | ★ | ★★★ |
| 服务端/客户端边界 | ★★ | ★ | ★★★ |
| 网络同步 | ★★★ | — | ★★ |
| 存档格式与迁移 | ★★ | ★★★ | ★★ |
| mod 生态理解 | ★ | ★★ | ★★★ |

### 10.3 本文新增的对照推断清单

为便于区分，以下结论是本文**横向比较得出**的、四份源文档都没有直接写的：

1. **"不换通用引擎"分主动型与被动型**，判据是"迁移代价在资产/数据结构，还是在能力缺口"（§1.2）。
2. **四家共同模式是"换平台层、冻结内容架构"**，并由此推出"重写内容层是高危更新"（§1.3）。
3. **构建期 vs 运行时的分野决定社区性格**：运行时→轻资产快迭代但碎片化；构建期→依赖工具链；脚本即内容→逻辑型社区（§2.2）。
4. **世界模型是存档格式、联机同步单位、mod 能力边界三者的共同因变量**（§3.2–3.4）。
5. **四种劝退点分属动机型/认知型/节奏型/知识型**，并对应四句"缺什么"（§4.3）。
6. **驱动力光谱与引导强度成反比**（§4.4）。
7. **更新形态是进度结构的必然产物**，不是团队喜好（§5.2）。
8. **像素一致性来自限制系统而非画功**，且三家的"限制维度"与"崩坏方式"一一对应（§6.2）。
9. **音乐是设计范式的听觉投影**（§6.5）。
10. **"要不要自研/重写"是团队规模判断，不是技术判断**（§7.2）。
11. **兼容压力 ≈ 内容累积年数 × 更新频率 ÷ 可外移程度**（§7.3）。
12. **mod 侵入性光谱**（数据覆盖→脚本注入→IL 补丁→源码分支），每一级是"能力换稳定性/合法性"（§8.2）。
13. **"能力最强"有两个答案**：单次改造深度看 Mixin/tModLoader，可持续能力看 tModLoader（§8.3）。
14. **生态规模 = 技术门槛可及性 × 内容需求 × 分发渠道 × 官方态度**，技术前提必要非充分（§8.4）。
15. **学习路线应按"终点"选而非按"起点难度"选**（§9.1）。
