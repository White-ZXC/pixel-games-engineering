# 《我的世界》Java 版：工程与设计深度解析

> 面向有编程基础、希望从工程与设计角度真正理解这款游戏的人。
> 主线为 Java 版，基岩版只在必要处作对照。
>
> **版本基准**：以 Java 版 1.18 – 1.21.x 的机制为主体，兼顾 2026 年起启用的「年份版本号」体系（26.x）。
> **标记约定**：
> - **【官方】** —— Mojang 的更新日志、官方文档、官方声明里明确写过的。
> - **【社区】** —— 社区文档（Minecraft Wiki、Fabric/Forge 文档）、反编译阅读、长期形成的共识。可信度高，但不是官方承诺。

## 0. 结论式概览

先给结论，后面逐条展开论证。

1. **它不是「用引擎做的游戏」，而是「一个 voxel 专用的自研引擎 + 一层数据驱动的内容层」。** 引擎部分（区块、光照、渲染、网络）高度特化且与游戏逻辑耦合；内容部分（方块状态、配方、战利品表、世界生成参数）被一层层剥出来做成 JSON。这个「一半硬编码、一半数据驱动」的分界线，是理解整个项目的钥匙。

2. **Java 是历史选择，不是技术最优解。** 2009 年的快速原型 + 跨平台 + 当时浏览器内可运行的 Java applet，让它选了 Java；代价是 GC 压力、JIT 预热、缺乏值类型。但它在 2011 年之后意外地变成了最大资产：JVM 字节码可注入（Mixin）、可反射、可反编译，这直接定义了今天 mod 生态的形态。

3. **有四次工程分水岭**，读源码/读更新日志时按这四条线切分最省力：
   - **1.13**：LWJGL 2 → LWJGL 3；数字方块 ID → 命名空间 ID（Flattening）；引入数据包。
   - **1.17**：渲染管线改成 OpenGL 3.2 core profile（全 shader）；最低 Java 16。
   - **1.18**：地形生成从「高度图 + 2D 生物群系」重写为「三维噪声 + 密度函数」。
   - **1.20.5**：最低 Java 21；物品 NBT → 数据组件（Data Components）；协议新增 configuration 阶段。

4. **资源包与数据包的分界线是「客户端资产 / 服务端逻辑」，根因是单人游戏跑的是一个真正的内置服务器。** 服务器不能假设客户端装了什么，所以服务端内容必须自成体系。这条约束解释了之后几乎所有「为什么这个能改、那个不能改」的问题。

5. **16×16 是风格契约，不是引擎限制。** 引擎支持任意分辨率贴图；16 是美术与 mipmap、视距、可辨识度共同收敛出的默认值。

6. **「没有主线目标」不是偷懒，是一套设计策略**：用「能力的质变」替代「数值的成长」，用「世界可改造」替代「关卡可通关」，用红石/农场/建筑这类涌现系统替代任务链。

7. **「同一个种子同一个世界」是版本内命题，不是跨版本承诺。** 同版本 + 同世界生成设置 + 同版本的游戏逻辑才成立；跨版本、跨平台（Java vs 基岩）都不成立。

8. **Mod 生态的分裂是治理问题，不是技术路线问题。** NeoForge 于 2023 年 7 月从 Forge 分家，1.20.2 起包名改为 `net.neoforged.*`，两边的 mod 从此互不通用。

9. **学习顺序建议：数据包 → 资源包 → 简单 mod → Mixin → 读世界生成。** 这条路径的每一步都能独立产出可见结果，且前一步的知识是后一步的必要前置。

## 1. 技术与构建

### 1.1 为什么是 Java

**【官方】** Java 版由 Markus Persson（Notch）在 2009 年用 Java 编写，运行在 JVM 上，图形/输入/音频通过 LWJGL 访问系统接口。

选择 Java 的合理性在当时非常具体：

- **零安装分发**。2009 年的 Java applet 可以让玩家在浏览器里点开就玩，这在 Flash 之外几乎没有对手。
- **一份代码跑三平台**。Windows / macOS / Linux 不需要各写一套原生层。
- **开发速度**。对一个人做原型来说，「不用管内存、不用管编译链」比「性能」重要得多。

代价同样具体，而且一直没消失：

- **垃圾回收**。区块、实体、粒子、NBT、字符串会产生大量短命对象，GC 停顿直接表现为卡顿。这也是为什么社区性能模组（Lithium、Sodium）第一件事往往是「少分配」而不是「少计算」。【社区】
- **JIT 预热**。冷启动前几十秒性能明显偏低，服务器重启后有一段「热身期」。
- **缺值类型**。Java 没有真正的 struct / 值类型（Valhalla 项目长期未落地），坐标、向量、颜色都得靠对象或手写打包的 long。
- **JNI 边界**。LWJGL 是 JNI 封装，频繁跨边界调用有成本，所以引擎倾向「批量提交」。

**【社区/推断】** 但这个选择在 2011 年之后成了护城河：字节码可以被 ASM/Mixin 改写，类可以被反射和替换，混淆映射可读——这三件事让「不修改官方代码也能深度改造游戏」成为可能。如果当年选的是 C++，今天的 mod 生态会接近「源码级 fork」，门槛高一个数量级。

### 1.2 JDK 要求的演进

这条线非常干净，而且每一跳都有明确的工程动因。

| 游戏版本 | 最低 Java | 依据 | 动因（推断/官方说明） |
|---|---|---|---|
| ≤ 1.16.5 | Java 8 | 长期事实标准【官方】 | Java 8 是当时企业/消费端最稳的 LTS |
| 1.17 | Java 16 | 【官方】1.17 发布说明 | 需要新语言特性与更新的 JVM 实现；也是渲染重写的时间点 |
| 1.18 – 1.20.4 | Java 17 | 【官方】1.18 预发布说明中明确「游戏现在使用 Java 17」 | 17 是 LTS，收敛到长期支持版本 |
| 1.20.5 及以后 | Java 21，且必须 64 位 | 【官方】1.20.5 更新日志：「The game now requires Java 21」「requires a 64-bit Operating System」，内置 Microsoft Build of OpenJDK 21 | 21 是新一代 LTS；64 位要求与内存占用增长有关 |
| 26.x（年份版本号） | 不低于 21，具体待考 | 【待考】 | 需自行查阅对应版本的官方发布说明 |

几点值得注意：

- **官方从某个版本起在启动器里内置 JRE**，玩家不需要自己装 Java。具体从哪一版开始默认内置【待考】，与 1.17 前后引入独立 Java 运行时的时间线接近。
- **「最低要求」和「推荐版本」不是一回事**。Fabric 官方 wiki 的建议是 1.17–1.20.4 用 Java 17、1.20.5+ 用 Java 21。【社区】
- **mod 开发者的 JDK 必须 ≥ 游戏要求**，且 Gradle 工具链要显式声明，否则会出现「能编译不能跑」的 `UnsupportedClassVersionError`。

### 1.3 渲染与引擎：为什么至今没有通用引擎

**【官方】** Java 版从 1.13 起使用 LWJGL 3（快照 17w43a 前后，官方日志明确写了「升级到最新版 LWJGL」）。从 1.17 起（快照 21w10a）使用 **OpenGL 3.2 core profile**，官方原话是「所有固定功能渲染都被基于 shader 的渲染取代」。

也就是说，渲染栈的演进是三步：

1. **LWJGL 2 + 固定管线时代**（约 2009 – 1.12）：`glBegin/glEnd` 那套思路的等价物，靠内置矩阵和固定光照。
2. **LWJGL 3 + 过渡期**（1.13 – 1.16）：输入/窗口/上下文现代化，但渲染仍是半固定管线。
3. **OpenGL 3.2 core + Blaze3D/RenderSystem 抽象**（1.17 起）：所有绘制走 shader，`RenderSystem` 成为唯一的图形 API 门面；核心 shader 以 `assets/minecraft/shaders/core/*.json` + `.vsh`/`.fsh` 的形式存在，**可以被资源包替换**。【社区，格式可从官方资源包结构中直接观察】

为什么不做成通用引擎？四个理由，按重要性排序：

- **voxel 的需求和通用引擎正交。** 区块网格化（把 16×16×16 的方块压成少量三角面）、按距离流式加载卸载、逐方块光照传播、海量小批次合并——这些在 Unity/UE 里都要写大量自定义代码，收益还不如自己写。
- **引擎和玩法逻辑深度耦合。** 方块更新、光照更新、区块加载次序都直接参与游戏规则（比如红石的更新顺序、光照影响刷怪）。抽成通用引擎等于把「规则」和「实现」分离，成本极高。
- **迁移成本 vs 收益**。一个已经上线十几年的产品，重写渲染层是「高风险、玩家不可见」的投入。1.17 的 OpenGL 3.2 重写已经是一次相当大的赌博。
- **mod API 依赖内部结构。** 生态的稳定性建立在「类名、方法签名、调用点」上，换引擎等于让生态归零。

**【社区】** 渲染层的实际结构大致是：区块网格构建在工作线程完成，上传到 GPU 在主线程完成；每个 section 是 16³；面剔除靠邻接方块查询，不使用 greedy meshing（因此几何量比理论最优大，但实现简单、可增量更新）。这也是 Sodium 能大幅提升帧率的空间所在——它把整个区块渲染器重写了。

**基岩版对照**：基岩版是 C++ 实现，跨平台（含移动端/主机），渲染器为 RenderDragon（逐步替换旧渲染器的过程发生在 2020 年前后，具体版本号【待考】）。两版在红石行为、世界生成、命令语法上都有实质差异，最典型的是 Java 存在 quasi-connectivity（区块内相邻红石元件的「意外」联动），基岩版没有。【社区，长期共识】

### 1.4 构建与反编译：混淆、Mojmap、Fabric/Forge 的映射方案

**混淆机制**

**【官方】** 发布给玩家的 jar 是经过混淆的：类名、方法名、字段名被替换成 `a`、`b`、`aa` 之类。具体混淆器【社区】普遍认为是 ProGuard，官方未在文档中强调这一点。

**官方映射（Mojmap）**

**【官方】** 2019 年 9 月起（快照 19w36a 起，官方公告标题为「Buzzy Bees 现已登陆 Java 版」，其中 Modding 段落明确写：「我们决定随未来所有版本发布游戏的混淆映射」），Mojang 开始随版本发布 obfuscation maps。这就是后来 mod 圈说的 **Mojmap / 官方映射**。

这份映射的价值与局限：

- **价值**：`net.minecraft.world.level.Level` 这种可读名字有了官方来源，不必再等社区猜。
- **局限 1**：**不含参数名**。方法参数仍是 `p_12345_` 之类。社区用 **Parchment** 补参数名。【社区】
- **局限 2**：**不含注释/文档**。语义仍要靠读代码。
- **局限 3**：**不改变「混淆后二进制」的事实**，你拿到的仍是混淆 jar + 映射表，需要自己 remap。

**三套映射方案的分工**

| 方案 | 归属 | 命名风格 | 谁在用 |
|---|---|---|---|
| **Mojmap（官方映射）** | Mojang | 官方可读名，如 `Level`、`BlockPos` | Forge 1.17+、NeoForge、Fabric 可选 |
| **Yarn** | Fabric 社区 | 另一套可读名，风格更「按语义重命名」，如 `World`、`BlockPos` | Fabric 默认 |
| **SRG / MCP 名** | MCP 时代遗产 | 中间名 + 社区名双层 | 老版本 Forge（1.16 及更早为主） |

**【社区】** 历史脉络：MCP（Mod Coder Pack）时代靠社区给的 `csv` 映射，Forge 长期使用 SRG 中间名保证「跨版本方法 ID 稳定」；1.17 之后 Forge 迁移到官方映射；Fabric 从 1.14 起就用 Yarn，并提供 Loom 构建插件自动完成「混淆 jar → 命名 jar」的 remap。

**反编译工具链**

- **Vineflower**（FernFlower 的现代分支）：Forge 生态长期默认。
- **CFR / Procyon**：单文件快速反编译，适合「只想看一个类」。
- **Linkie**：在 Mojmap / Yarn / SRG 之间互查名字，跨教程时非常有用。
- **Ornithe / Legacy Fabric**：为老版本维护映射与构建链，想研究 1.8 甚至 Beta 时代代码时的入口。

**法律边界**：Mojang 的 EULA 与 modding 指引允许制作和分发 mod，但**不允许分发游戏本体或反编译后的源码**。你可以在本地反编译研究，不能把反编译结果打包发布。【官方 EULA 精神，具体条款建议自行核对原文】

### 1.5 资源格式：贴图、模型、blockstate，以及资源包 vs 数据包

这是最能体现「分层设计」的部分。

**贴图与动画**

- 方块/物品贴图是 **PNG**，默认 16×16。
- 动画贴图用同名 **`.mcmeta`** 文件描述：

```json
{
  "animation": {
    "framerate": 10,
    "interpolate": true,
    "frames": [0, 1, 2, 3, 2, 1]
  }
}
```

贴图本身是**竖向拼帧**：宽度 = 单帧宽，高度 = 帧数 × 单帧高。`interpolate` 决定是否在帧之间插值（水、岩浆常用）。【官方格式，社区文档有完整字段说明】

**模型 JSON**

方块/物品的几何由 `assets/<namespace>/models/block|item/<name>.json` 定义：

- `elements`：每个 cuboid 的 `from`/`to`（0–16 的局部坐标）、`faces`（每面的 `uv`、`texture`、`cullface`、`tintindex`）、`rotation`。
- `parent`：继承另一个模型，覆盖局部字段。**这是资源包能极小体积改一个方块的关键**。
- `textures`：变量表，把 `#all`、`#side` 之类的占位符映射到实际贴图路径。
- `display`：手持/物品栏/掉落物时的变换矩阵。

**blockstate JSON**

`assets/<namespace>/blockstates/<name>.json` 只做一件事：**把方块状态映射到模型**。

- `variants`：精确匹配状态组合（如 `facing=north,half=bottom`）→ 单个模型或模型数组（数组 = 随机权重）。
- `multipart`：按条件组合多个模型（栅栏、红石线、墙）。

职责划分一句话总结：**blockstate 管「逻辑状态 → 用哪个模型」，模型管「长什么样」，贴图管「像素」。** 三者分离的好处是：改贴图不动几何，改几何不动状态逻辑，改状态逻辑不动美术。

**1.21.4 的变化【官方】**：物品模型从 `models/item/` 的硬编码路径改成 `assets/<namespace>/items/<name>.json` 的**物品模型定义**，由物品的 `minecraft:item_model` 组件选择。旧的 `models/item` 只在被引用时生效，「只做重定向」的物品模型被删除。这是资源包作者近年最大的一次迁移。

**资源包 vs 数据包：切在哪，为什么切**

| | 资源包（Resource Pack） | 数据包（Data Pack） |
|---|---|---|
| 作用端 | 客户端 | 服务端（单人 = 内置服务端） |
| 路径 | `assets/<ns>/...` | `data/<ns>/...` |
| 管什么 | 贴图、模型、blockstate、物品模型定义、音效文件与 `sounds.json`、语言文件、字体、shader、atlas 配置 | 配方、战利品表、进度、标签、函数（`.mcfunction`）、结构、世界生成（`worldgen/`）、伤害类型、附魔（1.21 起部分内容进入数据包注册表）【官方】 |
| 生效条件 | 客户端加载 | 服务端加载；**服务器上装的数据包，客户端不需要装** |
| 版本号 | `pack.mcmeta` 的 `pack_format` | 同左，但两者格式号各自独立演进 |

**为什么这么切？** 根因是：**单人游戏跑的是一个真的内置服务器**（IntegratedServer），多人游戏的专用服务器根本不渲染画面。因此：

- 任何「影响世界规则」的内容必须放在服务端能独立执行的地方 → 数据包。
- 任何「影响画面表现」的内容必须是客户端本地资源 → 资源包。
- 服务器没法给你发贴图（协议里没有「传资源」这一说），所以服务端内容只能引用「客户端本来就有的东西」（原版贴图、原版音效）。

**【官方】** 数据包是 1.13 开发周期引入的（与 Flattening 同期，具体快照号【待考】）。在此之前，服务端改内容只能靠插件 hook 或硬编码，这是 Bukkit 生态存在的重要原因。

### 1.6 多人架构：客户端/服务端职责划分

**同构代码 + 内置服务器**

Java 版是**同一份代码**同时充当客户端与服务端，靠「逻辑侧 / 表现侧」区分：

- `ServerLevel` 持有真实世界状态（方块、实体、tick）。
- `ClientLevel` 是服务端状态的**镜像**，用于渲染和本地预测。
- 单人游戏 = 启动一个 `IntegratedServer`，走的是和联机**完全相同的网络路径**（本地回环）。所以单人也会有「延迟」和「tick 卡顿」，因为逻辑真的在另一个线程/另一侧跑。

理解这一点，很多「玄学」就消失了：单人掉帧时怪物也会卡住，是因为 tick 被阻塞；`/tick` 命令能冻结世界，因为它在服务端侧。

**协议**

**【社区，协议文档为社区维护】** Java 版协议是自定义的 TCP 二进制协议：

- 默认端口 **25565**。
- 握手后用 VarInt 长度前缀的包（Packet）通信。
- 登录阶段协商**加密**（AES/CFB8，密钥用服务端 RSA 公钥加密传输）与**压缩**（zlib，超过阈值才压）。
- 1.20.5 起新增 **configuration 阶段**【官方】：登录成功后先进入配置阶段（下发数据包、资源包信息、注册表），再进入 play，解决「注册表内容在 play 阶段才同步」的历史问题。
- **协议版本号每次发布都会变**，所以客户端与服务端版本必须匹配（或使用 ViaVersion 之类的协议转换层）。

**权威模型**

- 服务端权威：移动、挖掘、容器操作最终由服务端判定。
- 客户端有**有限预测**：移动会本地先行，挖掘有进度预测，但服务端可以回滚（这也是「方块回弹」的来源）。
- 反作弊天然困难：协议公开、客户端可改、判定在服务端但信息来自客户端。

**服务端的三种形态**

| 形态 | 能否加方块/物品 | 装什么 | 典型用途 |
|---|---|---|---|
| 原版服务端（vanilla server.jar） | 否（只能靠数据包改已有内容） | 数据包 | 原汁原味联机 |
| 插件服务端（Spigot/Paper，Bukkit API） | 基本不能（只能模拟/替换） | 插件（JAR） | 大型公共服务器、小游戏 |
| Mod 服务端（Fabric/NeoForge） | 能 | mod + 数据包 | 整合包联机 |

**基岩版对照**：基岩版用「Add-ons」（行为包 + 资源包）替代 mod，能力受官方 API 限制，但可以跨平台联机，且服务端（BDS）是独立二进制。

## 2. 玩法与系统设计

### 2.1 核心循环与进度曲线

Minecraft 的进度不是一条线，而是**三条时间尺度叠加**：

| 尺度 | 循环 | 玩家获得的「质变」 |
|---|---|---|
| 分钟级（0–30 分钟） | 打树 → 工作台 → 木镐 → 石镐 → 石质工具 | 从「徒手」到「能挖铁」 |
| 小时级（1–10 小时） | 铁 → 钻石 → 下界 → 烈焰棒 → 末影珍珠 → 末地 | 从「一个维度」到「三个维度」 |
| 十小时级（10 小时+） | 附魔、酿造、村民交易、刷怪塔、红石自动化、建筑 | 从「手动获取」到「自动生产」 |

关键设计特征：

- **升级是能力质变，不是数值加成**。木镐 → 石镐不是「+20% 速度」，而是「能挖铁矿石」。铁镐 → 钻石镐是「能挖黑曜石 → 能进下界 → 能去末地」。这种「门」比数字更清晰，也更容易被玩家自己感知。
- **旁支系统（附魔、红石、酿造、村民）不是主线，但能反向加速主线**。附魔提高采集效率，红石自动化把重复劳动变成设计问题。这是「可选但高回报」的经典结构。
- **失败成本低**。死亡掉物品但有 5 分钟找回窗口、有床作为复活点、有 `/keepInventory` 之类的开关。低惩罚鼓励试错，试错产生故事，故事带来传播。
- **曲线的弱点**：中期（钻石 → 下界合金）容易变成「重复挖矿」，这是社区长期批评的点。【社区】

**1.16 之后的变化**：下界合金（Netherite）把「终局装备」从钻石推到远古残骸，等于给中期加了一段「高风险高回报」的采集；1.20 的锻造模板（Smithing Template）又给装备升级加了「必须先找模板」的门槛。【官方】

### 2.2 「没有主线目标」的设计哲学

**【官方】** 游戏内确实有一组「进度（Advancement）」，但它们的设计目的更接近**引导与提示**，而不是强制任务链。击败末影龙是一个「可以去做」的目标，不是「必须做」的终点。

靠什么驱动玩家自驱？可以拆成五个机制：

1. **可见的能力增长**。工具等级、附魔光效、装备外观，都是即时可见的反馈。玩家能清楚感到「我变强了」。
2. **世界的可改造性**。任何方块都能拆、能放，这意味着「想法 = 可实现」。这是沙盒最核心的承诺。
3. **涌现系统**。红石是图灵完备的计算介质，刷怪塔/农场/自动分类是「玩家自己发明的工程问题」。游戏提供规则，玩家提供目标。
4. **不确定性带来的叙事**。地形、洞穴、结构、怪物组合每次不同，玩家会自发讲述「我那次在洞里遇到……」。这是程序化生成的最大收益。
5. **社交与展示**。多人服务器、建筑分享、地图/整合包，把「玩」延伸成「创作与社交」。

**代价**：新玩家容易「不知道干什么」。Mojang 的应对是渐进式的——配方书（Recipe Book）降低合成门槛、进度系统给短目标、教程世界/提示。但这些都只是「降低迷路概率」，没有改变「沙盒优先」的设计取向。【官方+社区观察】

**对比视角**：这条路线和「主题乐园式」设计（明确关卡、明确奖励）是两种范式。Minecraft 选的是「玩具」而不是「游戏」——提供规则和材料，乐趣来自玩家自己定义问题。代价是留存曲线更依赖玩家类型。

### 2.3 世界生成：噪声、群系、种子确定性

**演进三阶段**

1. **2D 高度图时代**（早期 – 1.17）：地形高度由一个 2D 噪声图决定，群系按温湿度等 2D 参数划分。
2. **1.18 重写**：地形变成**三维**的。官方在 1.18.2 的日志里明确提到新增 `noise_router`（噪声路由器）与 `DensityFunction`（密度函数）注册表，并说「洞穴由这些密度函数组合而成」。【官方 1.18.2 更新日志】
3. **1.18.2 起**：`worldgen/noise_settings` 可被数据包覆盖，洞穴/地形参数从硬编码变成**数据驱动**。【官方】

**噪声函数的具体形态**

- **【社区】** 底噪仍是 Perlin 噪声（Ken Perlin 的 improved noise），以多八度叠加（octave/amplitude）的方式组合。1.18 的 `noise` 配置里能直接看到 `firstOctave` 与 `amplitudes` 数组，本质就是「起始频率 + 每个八度的振幅」。
- **1.18 的群系选择**用的是 5 维（实际是 6 个参数，其中一组用于深度）网格：**temperature、humidity、continentalness、erosion、depth、weirdness**。每个群系在世界生成参数里声明自己占据的参数区间，落在哪个格子就是哪个群系。这套方法让「山脉、海岸、内陆」在统计上更自然，而不是靠手写规则拼出来。【社区，代码与数据包格式可验证】
- **地形形状**则由 `density_function` 组合：基础噪声 + spline 映射（把噪声值映射成高度/密度曲线）+ 挤压/放大，最终得到「哪里是实心、哪里是空气」。

**种子确定性怎么保证**

- **【官方】** 同一个种子在**同一版本、同一世界生成设置**下生成同一个世界。
- 实现上，种子被用作所有随机源的根：地形噪声、结构位置、矿石分布、植被，各自用「种子 + salt」派生出独立的随机流，避免互相干扰（否则改一个矿石参数会挪动所有结构）。
- **结构**用 `structure_set` 的 `spacing` / `separation` / `salt` 决定「网格 + 抖动 + 随机跳过」，所以「同种子同结构位置」是设计出来的，不是巧合。

**必须强调的边界**（很多教程讲错的地方）：

- **跨版本不保证**。1.17 的种子在 1.18 会生成完全不同的地形，因为算法换了。【官方+社区】
- **跨平台不保证**。Java 与基岩版同种子不同世界，这是官方 FAQ 级别的问题。【官方】
- **改世界生成设置（数据包）也会改变结果**，因为参数变了。

**工程权衡**：确定性的代价是「必须避免任何依赖时间/迭代顺序/多线程竞态的随机」。所以世界生成被设计成「按区块坐标纯函数式推导 + 阶段化管线」，而不是「边生成边随机」。这也是为什么区块生成能并行——每个区块的输入只有种子和坐标。

## 3. 美术设计

### 3.1 16×16 的规范与限制

**先纠正一个常见误解**：16×16 不是引擎硬限制。资源包可以任意分辨率（32×、64×、甚至 512× 的「写实材质包」都跑得动）。【官方：资源包支持自定义分辨率】

16 之所以成为默认，是几个约束的交点：

- **尺度契约**：一个方块 = 1 米 = 16 像素，意味着「1 像素 ≈ 6.25 厘米」。这个比例让「栅栏高度、台阶厚度、门宽」在视觉上自洽。
- **mipmap 与视距**：远处方块会被 mipmap 降采样。分辨率越高，远处越容易「糊成一团」或闪烁（噪点），因为细节在降采样时互相抵消。
- **可辨识度**：16×16 只够画「大形状 + 少量材质暗示」，逼着美术用最少的元素建立识别。这反而提高了辨识度。
- **工作量**：方块数量以千计，16×16 让「整套贴图」成为一个人可完成的项目。

### 3.2 调色板约束与可辨识度

**【官方】** 1.14 的「Texture Update」由 Jasper Boerstra（Jappa）主导，重制了大量方块贴图。官方描述的目标包括「更一致的风格、更好的可读性」。

**【社区/美术经验】** 从重制前后的对比能总结出这套「Minecraft 式」的调色板方法：

- **每块 4–8 色**。超过这个数，16×16 里就会变成噪点。
- **明度阶梯优先于色相跳跃**。同一个方块内部用「亮部/中间调/暗部」三档明度，颜色只在同一色相内微调。这样在远处缩小后仍然是一个「色块」，不会散。
- **三面区分**：顶面最亮、侧面中间、底面最暗（引擎自带的方向光其实只做了一部分，贴图本身的明度差贡献很大）。这是「方块有体积」的核心暗示。
- **类别色锚点**：石类=灰、木类=棕、金属=冷灰+高光、矿物=石底+彩色斑点。玩家靠「颜色类别」在 0.5 秒内完成识别。
- **避免高频细节**。随机噪点会让贴图在 mipmap 下变灰；有意的「结构性」图案（砖缝、木板纹、矿石斑点）才能在缩小后存活。
- **轮廓靠「边」**。岩石类方块通常在边缘画一圈更暗的像素，用来和相邻方块分离；草方块侧面用渐变（草色 → 土色）解决「接缝」问题。

**常见失败模式**：色相跳变过大（远看是花的）、细节密度过高（远看是灰的）、明度太平（近看是贴纸）、忽略相邻方块的接缝（铺一片像马赛克）。

### 3.3 生物与 UI 的视觉识别

**生物**

- 模型是**盒子（cuboid）+ 逐面 UV 展开**。所以生物贴图不是「画一只猪」，而是「画一张猪的展开图」——六个面各占一块矩形，美术必须脑内做 3D 展开。这也是为什么很多自制生物模型看起来「接缝错位」。
- **动画是代码里的关键帧**（走路、摆臂、扭头），不是数据驱动。所以「加一个新生物」不是纯资源包能完成的，必须有代码侧支持。【社区，反编译可验证】

**识别度怎么建立**：

- **剪影（silhouette）**：苦力怕的直立长方体、末影人的细高、蜘蛛的多足。缩小到 16 像素也能认出。
- **单一强调色**：苦力怕的绿、末影人的黑+紫眼、史莱姆的半透明绿。一个生物一个主色，不混。
- **眼睛高光**：几乎所有被动生物都有「两点白」的眼睛，这是「可爱/无害」的信号；敌对生物则用纯色或发光眼。

**UI**

- **像素字体**：默认字体是位图字体，UI 的「像素感」来自字体而不是贴图。
- **九宫格拉伸**：按钮、面板用 9-slice（四角不拉伸，边和中心拉伸），保证任意尺寸不变形。
- **1px 描边 + 投影**：文字有暗色描边/阴影，保证在任何背景上可读。
- **GUI Scale**：官方提供缩放档位，因为不同分辨率下像素密度差异巨大。

**风格如何维持统一**：不是靠一份规范文档，而是靠**同一批人 + 同一套栅格 + 同一套调色习惯**。【社区/推断】这也是为什么第三方资源包很难「像原版」——它们缺少的不是技术，是那套隐性的约束。

## 4. 音乐与音效

### 4.1 C418 的作曲思路

**【官方/公开资料】** 原声由 Daniel Rosenfeld（C418）创作，代表作是《Volume Alpha》（2011）与《Volume Beta》（2013）。他的思路常被概括为：

- **极简动机 + 长发展**。一个很短的和弦进行或旋律片段，用几分钟慢慢展开、叠加、消散。
- **大量留白**。音量低、织体稀疏，让「环境音」和「玩家自己的动作声」成为主角。
- **电子音色 + 钢琴**。合成器的柔和 Pad 与钢琴单音，制造「温暖但孤独」的气质。
- **不追求「主题曲」式的记忆点**，而是追求「你在挖矿时不会烦」。

这套音乐和「无限沙盒」的体验高度契合：它不叙事，不推动，只是陪着你。

### 4.2 后续作曲家与轮换

**【官方】** 1.16（下界更新）起，Mojang 引入了新的作曲者，Lena Raine 为下界创作了曲目；1.20/1.21 时期的 Trial Chambers 相关音乐由 **Kumi Tanioka、Lena Raine、Aaron Cherof** 三人参与（官方有专门的「Composing the Trial Chambers」文章）。此外唱片还出现了 Samuel Åberg、Amos Roddy、Hyper Potions、fingerspit 等名字。【社区整理，逐曲归属以官方曲目表为准】

**【社区报道】** C418 已不再为游戏创作新曲，原因被广泛报道为与版权/合作条件有关，但官方未做详细说明，**具体原因【待考】**。

**风格是否统一**：新作曲者的加入带来更「氛围/合成器」的方向，但都遵守同一条隐形规则——**低频、慢速、不抢戏**。这是「Minecraft 音乐」听起来仍然是 Minecraft 的原因。

### 4.3 环境音乐的触发条件

**【社区，长期验证】** 背景音乐不是循环播放，而是由客户端的音乐调度器在满足条件时**随机间隔触发**：

- 典型间隔在**约 10–20 分钟**量级（具体 tick 数随版本变动，【待考】），且带随机抖动，避免可预测。
- 曲目按**维度/环境**分组：主世界、下界、末地、水下、菜单各有曲库。
- 特定场景有专属曲目（如末地、下界的新曲目在对应维度才可能播放）。
- 创造模式同样会播放。
- 洞穴环境音（`ambient.cave`）是另一套机制：随机触发、与封闭/黑暗环境相关，用来制造「不安」。

**工程上值得注意**：音乐调度器在客户端侧，所以「服务器无法强制给某个玩家放某首歌」（除非用资源包 + 命令播放 sound event）。

### 4.4 音频格式与空间化

**【社区，可从资源包结构直接验证】**

- **格式**：OGG Vorbis（`.ogg`）。音乐与音效都在 `assets/<ns>/sounds/` 下。
- **`sounds.json`**：把「声音事件名」（如 `block.stone.break`）映射到「文件列表 + 音量/音高范围 + 权重 + 是否流式」。多个文件 = 随机挑选，避免重复听腻。
- **流式播放**：长音频（音乐、唱片）标记 `"stream": true`，边解码边播，不整段载入内存。
- **空间化**：
  - **单声道文件**会被当作「点声源」，按听者位置做距离衰减 + 左右声像定位。
  - **立体声文件**会被当作「非位置化」（因为已经有左右信息），不随视角变化——所以环境音/音乐用立体声，音效用单声道。
  - `attenuation_distance` 控制衰减半径；超过范围听不到。

这条「单声道才空间化」的规则，是很多自制音效「听起来不对」的根本原因。

## 5. 工程与生态

### 5.1 团队规模与发布节奏

**团队变迁**

- 2009：Notch 单人原型。
- 2010：成立 Mojang。
- 2011-11-18：1.0 正式版发布（MineCon）。【官方】
- 2014：微软以 25 亿美元收购 Mojang。【官方】
- 现在：Mojang Studios，Java 版由专门团队维护。

**具体人数官方未公布**，社区估计 Java 版核心团队在「数十人」量级（程序、美术、音效、社区管理合计），**精确数字【待考】**，不建议在正式材料里写死。

**发布节奏**

- **快照（Snapshot）**：长期保持「大约每周一次」的节奏，用于测试下一个大版本。【官方】
- **预发布（Pre-release）/ 发布候选（Release Candidate）**：临近发布时切换，主要修 bug。
- **正式版 + 小版本（1.x.y）**：修紧急问题。
- **「Drop」模式**：近年出现「中型内容更新」独立成版（如 1.20.5 Armored Paws、1.21.x 的若干 drop），而不是一年一个大版本。
- **年份版本号（2026 起）**：官方宣布改为按年份编号，2026 年的版本以 `26` 开头（如 26.1、26.2）。基岩版与 Java 版后续位数不同，因为发布节奏不同。【官方】

**工程意义**：每周快照 = 高频集成 + 高回归风险，这要求自动化测试与内部工具链足够强；同时也解释了为什么 mod 生态「跟不上」——每次快照都可能改动内部结构。

### 5.2 Mod 生态：Forge / Fabric / NeoForge

**时间线**

| 时期 | 事件 |
|---|---|
| 约 2011 | **Forge** 出现，逐步统一了此前的 ModLoader 碎片 |
| 1.13（2018） | Forge 更新严重滞后，出现 **Rift** 等过渡方案 |
| 2018 末–2019 | **Fabric** 诞生，面向 1.14，主打「快速跟进 + Mixin + 轻量」【社区】 |
| 2020 | **Quilt** 从 Fabric 分叉（社区治理分歧）【社区】 |
| 2023-07 | **NeoForge** 从 Forge 分家，几乎整个 Forge 团队迁出【社区报道，NeoForge 官方有说明】 |
| 1.20.2 起 | NeoForge 包名改为 `net.neoforged.*`，与 Forge 的 mod 互不兼容【社区/官方】 |

**三者差异**

| | Forge | Fabric | NeoForge |
|---|---|---|---|
| 改造方式 | 打补丁（patches）+ 事件总线 | **Mixin**（字节码注入）+ 轻量 loader | 同 Forge 路线，但重构了注册表/能力系统 |
| API 体积 | 大而全，自带很多工具 | 极小，核心功能靠 Fabric API 补 | 大而全，现代化改造 |
| 更新速度 | 慢，历史包袱重 | 快，快照期就能跟进 | 比 Forge 快 |
| 映射 | 1.17+ 官方映射 | Yarn 默认 | 官方映射 |
| 典型场景 | 大型整合包、老牌 mod | 性能模组（Sodium/Lithium）、新 mod | 新一代大型整合包 |

**为什么会分裂？** 三个层次的原因，按可信度排列：

1. **治理与社区文化**（主因，NeoForge 方面的公开说法即指向此）。决策权集中、沟通方式、贡献者待遇，是团队出走的直接触发点。【社区/NeoForge 公开说明】
2. **更新速度与技术债**。Forge 的补丁式架构在版本快速迭代时维护成本极高，几乎每次大版本都要重做大量 patch。
3. **方向分歧**。1.20.2 的内部改动（注册表、能力系统）是重塑架构的窗口期，双方对「怎么改」没有共识，于是各走各路。

**顺带区分**：Bukkit/Spigot/Paper 是**服务端插件 API**，不是 mod loader——它们不能在客户端加内容，只能操作已有方块/实体/命令。Sponge 试图做「跨 loader 的抽象 API」。Sinytra Connector 试图让 Fabric mod 跑在 NeoForge 上（兼容层，非官方）。【社区】

## 6. 学习路径

### 6.1 值得读的资料

**官方**

- **Minecraft.net 的版本更新日志**：技术信息密度最高，每版都有「Technical Changes」，包含 data pack version / resource pack version、注册表变更、协议变更。**这是最被低估的一手资料。**
- **官方混淆映射**：随版本发布，直接给你可读类名。
- **官方 EULA 与 modding 指引**：明确边界。

**社区（按可靠性排序）**

1. **Minecraft Wiki（minecraft.wiki）**：技术细节最全，含方块状态、数据包格式、世界生成、协议摘要。**但要注意版本标注**，很多页面混合了多个版本的行为。
2. **Fabric Wiki / Fabric 文档**：环境搭建、Mixin 教程、Loom 配置，写得相当工程化。
3. **NeoForge / Forge 官方文档**：事件系统、注册表、数据生成（DataGen）。
4. **misode 的 mcmeta 仓库**：数据包/资源包 JSON 的 **schema 与版本差异**，查「这个字段在哪个版本加的」最快。
5. **技术向 Wiki（Technical Minecraft Wiki）**：红石、刷怪、机制细节的硬核研究。
6. **协议文档（wiki.vg 存档 / minecraft.wiki 的协议页）**：想写客户端/机器人时的唯一依靠。

**工具**

- 反编译：**Vineflower**、**CFR**
- 映射互查：**Linkie**
- 参数名：**Parchment**
- 建模：**Blockbench**（方块/实体模型，可直接导出 JSON）
- 贴图：**Aseprite** / Photoshop（16×16 建议关掉抗锯齿）
- 数据包调试：游戏内 `/reload`、`/datapack list`、`/worldgen` 相关命令

### 6.2 五个由浅入深的动手项目

**项目 1：做一个「像样」的资源包（1–2 天）**

- 目标：替换 3 个方块贴图 + 给一个方块加动画（`.mcmeta`）+ 用 `parent` 继承修改一个模型。
- 学到：`pack.mcmeta` 与 `pack_format`、atlas、模型继承、UV 布局、blockstate 到模型的映射。
- 验收：进游戏能看到自己的贴图，且不报「missing texture」。

**项目 2：做一个数据包（2–4 天）**

- 目标：自定义配方 + 战利品表 + 进度 + 一个 `.mcfunction`（比如「右键木棍触发传送」）+ 一个自定义维度（`worldgen/`）。
- 学到：命名空间、注册表、加载顺序、`/reload` 的边界（有些东西 reload 不生效，必须重启）。
- 验收：`/datapack list` 能看到它，配方在配方书里出现。

**项目 3：写第一个 Fabric mod（3–7 天）**

- 目标：注册一个物品 + 一个方块 + 一个创造模式物品栏标签 + 一个简单的 `BlockEntity`（比如会缓慢转动的方块）。
- 学到：注册表 API、`Identifier`、客户端/服务端分离（`ClientModInitializer` vs `ModInitializer`）、资源包与代码的配合。
- 验收：能合成、能放置、能存档（退出重进后状态还在）。

**项目 4：用 Mixin 改一个原版行为（3–5 天）**

- 目标：让某个方块的掉落翻倍，或修改某个 tick 逻辑。
- 学到：`@Inject` / `@Redirect` / `@ModifyVariable` 的区别、注入点选择、`@Shadow` 访问私有成员、为什么「注入点选错会崩」。
- 验收：行为改变，且不破坏其他逻辑；能解释清楚「注入在方法头还是返回值处，为什么」。
- 提醒：这是最容易被版本更新打断的一步，建议固定一个版本做完。

**项目 5：读世界生成代码 + 做一个小实验（1–2 周）**

- 目标：定位到 `NoiseBasedChunkGenerator`、`NoiseRouterData`、`DensityFunctions` 这几个类，读懂「密度函数如何组合成地形」；然后用数据包覆盖 `worldgen/noise_settings`，把海平面或地形幅度改掉。
- 学到：1.18 地形管线、密度函数组合、`worldgen` 数据包结构、确定性从哪来。
- 验收：能用一句话解释「为什么同一个种子在不同版本生成不同世界」，并能用数据包做出可见的地形变化。

**可选项目 6：写一个 Paper 插件（3–5 天）**

- 目标：一个 `/home` 传送插件。
- 价值：亲手体会「插件 vs mod」的边界——为什么插件加不了新方块，为什么它能跨版本更稳。

### 6.3 路线图

| 阶段 | 项目 | 难度 | 主要产出 | 前置 |
|---|---|---|---|---|
| 1 | 资源包 | ★ | 视觉改动 | 无 |
| 2 | 数据包 | ★★ | 规则改动 | 阶段 1 |
| 3 | Fabric mod | ★★★ | 新内容 | Java + Gradle |
| 4 | Mixin | ★★★★ | 改原版逻辑 | 阶段 3 |
| 5 | 世界生成 | ★★★★★ | 地形实验 | 阶段 2 + 4 |

| 版本 | 最低 Java | 渲染 | 映射生态 |
|---|---|---|---|

| 1.18–1.20.4 | Java 17 | 同上 | Fabric=Yarn，Forge=Mojmap |

### 7.2 目录结构速查

**资源包**

```
my_pack/
├── pack.mcmeta                     # pack_format 必填
└── assets/<namespace>/
    ├── textures/block|item|entity/...
    ├── models/block|item/...
    ├── blockstates/...
    ├── items/...                   # 1.21.4+ 物品模型定义
    ├── sounds/...
    ├── sounds.json
    ├── lang/zh_cn.json
    ├── font/...
    ├── shaders/core/...
    └── atlases/...
```

**数据包**

```
my_datapack/
├── pack.mcmeta
└── data/<namespace>/
    ├── recipe/            # 注意：不同版本目录名单复数有变化，务必查对应版本
    ├── loot_table/
    ├── advancement/
    ├── tags/
    ├── function/          # .mcfunction
    ├── structure/
    ├── worldgen/          # biome / noise_settings / density_function / ...
    ├── damage_type/
    └── enchantment/       # 1.21 起部分内容数据驱动
```

> 注：`recipe` / `recipes`、`loot_table` / `loot_tables` 这类单复数在不同版本之间改过，**这是新手最容易踩的坑**。以官方更新日志和 mcmeta schema 为准。
